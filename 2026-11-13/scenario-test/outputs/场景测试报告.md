## 1. 结论摘要

1. **主链路能跑通。** 四个场景共创建 20 条任务，10 条按可执行验收命令关闭（其中 1 条是弱验收，见 P1-14）；客户、报价、合同、开票信息、发票、回款整条商务链在 SC-001/002/004 上均能落库。
2. **但有 6 个 P0 级问题，其中 3 个直接决定能不能接真客户：**
   - 跨项目任务去重会把 A 客户的任务静默吞进 B 客户（实测 T-0137）；
   - 多项目一进来，公司级完成率、WBS 三方校验、飞书四处同步口径全部失真；
   - 闸门语义不一致：同一件事，`task add` 只警告，`plan` 直接整批拒绝；默认 `warn` 还导致 `doctor` 红灯。
3. **另有 3 个 P0 级链路缺陷：** 稠密检索一旦项目有自己的索引就丢掉 `company/`、`templates/` 全局资产；报价/合同可以不带客户和报价单仍通过商务闸门；建单强制填 `done_when`、关单又强制可执行命令，真实接单节奏被卡住。
4. **商务闸门不会因为“新项目没合同”直接把活锁死**：默认 `warn` 下 `task add` 仍能建 code 任务；但 `plan` 会硬拒。切到 `block` 后才会真正锁死，实测符合预期。
5. **多项目并行会互相污染**：任务归属（去重）、公司级指标、WBS 校验、商务汇总都受影响；向量检索的项目隔离本身是好的，但 dense 路径丢全局资产，属于另一种“污染”。
6. **验收命令机制可写、可执行**，10 条任务均通过退出码 0 关闭（其中 1 条是弱验收）；但 `test -s` 配 glob 在重跑产生多文件后会直接报错，且 `test -s` 对 `project init` 生成的空模板也能通过，存在假验收风险。
7. **快照上的 `doctor` 是红灯**：308 个测试中 2 个失败，失败点都是“默认 `warn` 与测试预期的 `block` 不一致”。

### 2.2 断点与添麻烦

**断点 1（P0-03）：`plan` 与 `task add` 对商务闸门的处理相反。**
```text
$ python3 agency.py plan --file _scenario_test/sc001-draftA.json --project SC-001 --days 14 --hours 40
...
[OK ] #5 质检记录数字化原型｜pm｜2026-11-18→2026-11-22｜8h
[拒绝] 商务闸门未通过：SC-001，本批含 code 任务，整批拒绝
整批拒绝：1 项，未写入任何任务
EXIT:1

$ python3 agency.py task add --title 质检记录数字化原型 ... --kind code
[警告] 商务闸门未通过：SC-001 未完成商务审查（warn 模式不阻断，强制请设 finance.gate_mode=block）
已建 T-0131｜质检记录数字化原型｜pm｜2026-11-18 → 2026-11-22
EXIT:0
```
同一项目、同一时刻、同一 `warn` 模式：`plan` 硬拒，`task add` 放行。这会让“用 plan 排期”和“逐条建单”得到相反结果。

**添麻烦 1（P1-13）：默认 5 天计划窗口装不下正常两周排期。**
```text
$ python3 agency.py plan --file _scenario_test/sc001-draftA.json --project SC-001 --hours 40
[错误] #4 排期与WBS拆解 ... - 日期超出窗口 2026-11-13~2026-11-18（5 天）
[错误] #5 质检记录数字化原型 ... - 日期超出窗口 2026-11-13~2026-11-18（5 天）
```
必须显式加 `--days 14`，否则默认值会把正常项目判为非法。

**假验收 1（P1-14）：`test -s` 对空模板也返回 0。**
```text
$ python3 agency.py task close T-0130 --evidence "计划文件存在" \
    --verify "test -s clients/SC-001-精密零部件厂/04-项目计划.md"
已关闭 T-0130（done），验收通过。
证据：计划文件存在｜验收: test -s clients/SC-001-精密零部件厂/04-项目计划.md｜exit 0｜
```
`04-项目计划.md` 是 `project init` 生成的模板，不代表任何交付。验收命令机制没有“内容级”约束，容易把“文件存在”当成“活干完”。

**时间显示（P1-12）：事实与闸门时间按 UTC 显示，日期比本地早一天。**
```text
$ python3 agency.py facts list --project SC-001
F-0005 [S1] 2026-11-12 SC-001｜质检记录目前全部纸质...（王厂长 2026-11-13 电话口述）
# 实际执行时间：2026-11-13 01:57（Asia/Shanghai）

$ python3 agency.py gate finance confirm SC-001 --by 龙奕
商务闸门已开：SC-001｜确认人：龙奕｜2026-11-12T17:57:38+00:00
```
库内 `created_at` 是 `2026-11-12T17:57:28+00:00`，列表直接截取前 10 位，得到 UTC 日期。对账时会差一天。

**商务单据脱链（P0-06）：报价可以没有客户，合同可以没有报价，闸门仍然放行。**
```text
$ python3 agency.py finance quote add SC-001 --amount 9800 --cost 3500 ... --client-id 
已建报价 Q-0002｜SC-001｜9800｜成本 3500

$ python3 agency.py finance contract add SC-001 --amount 9800 --quote-id  ...
已建合同 C-0002｜SC-001｜9800｜预付 50%｜账期 15 天

$ python3 agency.py gate finance confirm SC-001 --by 龙奕
商务闸门已开：SC-001 ...（全部通过）
```
库内实际值：`Q-0002.client_id = NULL`，`C-0002.quote_id = NULL`、`C-0002.client_id = NULL`。闸门取的是“项目最新一张报价”，并不校验合同是否关联该报价、金额是否一致。

### 2.3 场景一小结

- 真省事：`facts add` 的 S1/S2/S4 分级、`plan` 的依赖校验、`dispatch --dry-run`、`run` → `close` 的验收闭环、报价/合同/开票/回款台账。
- 真添麻烦：默认 5 天窗口、开票前必须先填开票信息、`task add` 强制验收标准、`task close` 强制可执行命令。
- 真走不通：含 code 任务的 `plan` 在 `warn` 模式下被硬拒；变更单（本场景未涉及，见场景二）。

### 3.2 断点与添麻烦

**断点 1（P1-08）：没有“变更单”实体。**
```text
$ python3 agency.py finance change add SC-002 --amount 3000 --reason 新增多语言知识库
usage: agency finance [-h] {quote,contract,invoice,payment,cost,billing,config,client,summary} ...
agency finance: error: argument finance_cmd: invalid choice: 'change'
```
实际只能“再建一张报价单 + 再建一批任务”，合同金额、付款节点、验收范围都不会自动跟着变。真客户一旦变更范围，平台没有可追溯的变更记录。

**断点 2（P0-01）：跨项目任务去重污染。**
```text
# SC-002
$ python3 agency.py task add --title 整理需求说明 --project SC-002 --owner pm \
    --start 2026-11-13 --due 2026-11-18 \
    --done-when "cmd: test -s clients/SC-002-跨境电商/01-需求说明.md"
已建 T-0137｜整理需求说明｜pm｜2026-11-13 → 2026-11-18

# 同一标题/owner/验收/截止，换到 SC-001
$ python3 agency.py task add --title 整理需求说明 --project SC-001 --owner pm \
    --start 2026-11-13 --due 2026-11-18 \
    --done-when "cmd: test -s clients/SC-002-跨境电商/01-需求说明.md"
已存在 T-0137（内容幂等，未重复建单）｜整理需求说明
```
去重哈希是 `title|owner|done_when|due`，**不含 project**。客户 A 的任务会被客户 B 静默吞掉，任务归属直接错。

**添麻烦 1（P1-09）：没有项目维度统计。**
```text
$ python3 agency.py task stats --project SC-002
agency: error: unrecognized arguments: --project SC-002

$ python3 agency.py finance summary --project SC-001
agency: error: unrecognized arguments: --project SC-001
```
公司级 `brief` / `stats` / `finance summary` 全部只给全局数，多客户并行时无法回答“SC-002 现在什么状态、还欠多少钱”。

**按设计拦截（不是缺陷）：开票信息前置校验。**
```text
$ python3 agency.py finance invoice add C-0003 --no SC002-001 --amount 8400 ...
开票信息不全（缺 title/tax_no/type），先补齐：
python3 agency.py finance billing set SC-002 --title <抬头> --tax-no <税号> --type <发票类型>
EXIT:1
```
提示清晰，补 `billing set` 后开票成功。

### 3.3 场景二小结

- 真省事：报价/合同/开票/回款链、商务闸门的自动核算（毛利、预付、账期、付款节点）、闸门撤销/重确认。
- 真添麻烦：没有变更单；没有项目维度统计；开票前必须单独补开票信息。
- 真走不通：`finance change` 不存在；变更只能靠“新报价 + 新任务”人工兜底。

| 12 | 向量索引 | `vector index clients/SC-003-外贸公司/询盘分流规则.md --project SC-003` | bge-m3 1024 维，新增 1 块 | 走通 |
| 13 | 稠密检索（同项目） | `vector search "询盘分流规则 客户诊断问卷 访谈提纲 30分钟诊断" --project SC-003` | 只返回 1 条 SC-003 文档，**没有任何 templates/company** | **断点（P0-04）** |
| 14 | 稀疏检索（同项目） | 同上加 `--provider hash` | 返回 8 条，前 8 全是 `templates/` 诊断问卷、访谈提纲、报价单模板 | 对照证据 |
| 15 | 从 SC-002 检索 | `vector search "询盘分流规则 东南亚 大客户队列" --project SC-002` | 无稠密索引，降级 hash；不返回 SC-003 文档 | 项目隔离 OK |
| 16 | 不带项目检索 | 同上不加 `--project` | SC-003 文档排第 1（0.766） | 全局可见 |

### 4.2 断点与添麻烦

**断点 1（P0-04）：一旦项目有自己的稠密索引，全局 `company/`、`templates/` 就消失。**
```text
$ python3 agency.py vector search "询盘分流规则 客户诊断问卷 访谈提纲 30分钟诊断" --project SC-003 --k 8
1. 0.690｜clients/SC-003-外贸公司/询盘分流规则.md#0｜# 询盘分流规则（SC-003 专属）...

$ python3 agency.py vector search "询盘分流规则 客户诊断问卷 访谈提纲 30分钟诊断" --project SC-003 --k 8 --provider hash
1. 0.429｜templates/诊断包验证记录.md#1｜...
2. 0.365｜templates/诊断包验证记录.md#0｜...
3. 0.358｜templates/访谈提纲-30分钟.md#0｜...
4. 0.353｜templates/报价单模板.md#0｜...
...
```
同一查询：dense 只命中项目自己的 1 条文档；sparse 命中 8 条全局模板。原因在 `vectors.py`：`_rows()` 的过滤是 `project_id = ? OR project_id IS NULL`，而 `_matrix()` 只取 `project_id = ?`。当项目有自己的 dense 行时，`_search_dense` 返回非空，就不会降级到 sparse，全局资产被静默丢掉，且没有 `[检索降级]` 提示。

**添麻烦 1（P2-16）：关掉前序任务后，下一条任务仍不能提前派。**
```text
# T-0138 已关闭，T-0139 start=2026-11-14，today=2026-11-13
$ python3 agency.py dispatch --project SC-003 --dry-run
没有可调度任务：依赖未关或不在 [start, due] 窗口内。
```
`dispatch_ready` 要求 `start <= today <= due`。单人公司提前干完活，不能把明天的任务拉今天做。

**断点 2（P1-10）：`dep add` 自动编号会撞已有编号。**
```text
$ python3 agency.py dep add --need "客户提供 20 条真实询盘样本" ... --due 2026-11-12
依赖编号已存在：D-0005

$ python3 agency.py dep add --id D-0007 --need "..." ... --due 2026-11-12
已新增依赖 D-0007：客户提供 20 条真实询盘样本（应提供 2026-11-12）
```
自动编号用 `COUNT(*)+1`，现有 D-0003～D-0006 共 4 条时算出 D-0005，正好撞号。多项目共用一个依赖台账时更容易发生。

**按设计拦截（不是缺陷）：失败验收命令拒绝关闭。**
```text
$ python3 agency.py task close T-0141 --evidence "SOP 已写" --verify "test -f /nonexistent/ops-sop.md"
验收命令退出码 1，拒绝关闭：test -f /nonexistent/ops-sop.md
```

### 4.3 场景三小结

- 真省事：`task add --dep` 建依赖链、`dispatch` 按依赖/窗口筛选、`run` → `close` 串行验收、`dep` 缺料台账。
- 真添麻烦：派活不能提前拉活；`dep add` 自动编号撞号；dense 检索丢全局模板。
- 真走不通：没有硬断点；运维任务因窗口/验收命令未关闭，属于流程未走完，不是平台报错。

## 5. 场景四：一人公司自身经营（找线索 → 内容发布 → 跟进 → 回款）

### 5.1 目标链路与实际走法

| # | 步骤 | 命令（摘要） | 实际结果 | 判定 |
|---|---|---|---|---|
| 1 | 建项目 + 录事实 | `project init SC-004`；`facts add` S3/S4 | F-0012、F-0013 | 走通 |
| 2 | 建 4 条经营任务 | 线索(scout)、内容(content)、跟进(longyi)、回款(longyi) | T-0142～T-0145 | 走通 |
| 3 | 派活预演 | `dispatch --project SC-004 --dry-run` | 只有 T-0142 @scout；内容任务 start=11-14 不在窗口 | 走通 |
| 4 | 跑 scout + 关闭 | `run scout` → `task close --verify grep` | 关闭成功 | 走通 |
| 5 | 跑 content + 关闭 | `run content` → `task close --verify grep` | 关闭成功 | 走通 |
| 6 | 再看派活 | `dispatch --dry-run` | `没有可调度任务`；T-0144/T-0145 owner=longyi 永远不出现 | **盲区（P1-11）** |
| 7 | 没合同直接开票 | `finance invoice add C-9999 ...` | `合同不存在：C-9999` | 按设计拦截 |

| 11 | 全局商务汇总 | `finance summary` | 已开票 26,100｜已回款 21,300｜未回款 4,800｜逾期 4,800 | 口径混算（P1-09） |

### 5.2 断点与添麻烦

**盲区（P1-11）：`owner=longyi` 的任务不会进入派活队列。**
```text
$ python3 agency.py task list --project SC-004
T-0142 [已完成] ... @scout 线索搜集：长三角精密制造
T-0143 [已完成] ... @content 内容发布：案例拆解
T-0144 [未开始] ... @longyi 客户跟进：首批线索
T-0145 [未开始] ... @longyi 回款跟进

$ python3 agency.py dispatch --project SC-004 --dry-run
没有可调度任务：依赖未关或不在 [start, due] 窗口内。
```
`dispatch_ready` 明确跳过非 Agent owner（`agency.py` 的 `is_agent_role`）。设计上“老板的活不派给 Agent”没问题，但平台没有给老板一个“今天该我干什么”的队列，跟进/回款任务只能靠 `task list` 自己翻。

**指标污染（P0-02）：四个测试项目把公司完成率从 95.3% 拉到 88.1%。**
```text
# 基线（副本原始 DB）
全部 115｜完成 101｜作废 9｜未完成 5｜完成率 95.3%
完成工时 191.0h

# 跑完四个场景后
全部 135｜完成 111｜作废 9｜未完成 15｜完成率 88.1%
完成工时 231.0h
```
新增的 20 条测试任务全部进入公司级分母；`brief` / `stats` 没有项目过滤，也没有“公司自身经营 vs 客户项目”的分线口径。对一人公司来说，这会直接误导经营判断。

**内部经营没有独立收入入口（P2）：**
```text
$ python3 agency.py finance invoice add C-9999 --no SC004-001 --amount 3000 ...
合同不存在：C-9999
```
要给“一人公司咨询收入”开票，必须先造一个客户 CL-0004、一张报价 Q-0005、一份合同 C-0004、一条开票信息。流程能走通，但“自有产品/自有咨询收入”被强行建模成客户项目，语义不自然。

### 5.3 场景四小结

- 真省事：scout/content 角色可直接跑；验收关闭闭环可用；商务链能完整落到回款。
- 真添麻烦：老板自己的任务没有派活队列；内部收入必须先造客户/合同；全局看板无项目维度。
- 真走不通：没有合同不能开票（按设计）；没有“自有收入”专门入口（可用客户项目绕过）。

### 6.1 多项目并行污染

### 6.2 闸门

| 问题 | 实测 | 结论 |
|---|---|---|
| 开工闸门 | 未确认时 `task add --kind code` 报 `开工闸门未通过`；确认后可建 | 可用，符合设计 |
| 商务闸门默认模式 | DB 中 `finance.gate_mode=warn`；`task add` 只警告，`plan` 硬拒 | 语义不一致（P0-03） |
| 商务闸门 `block` 模式 | `finance config --gate-mode block` 后，SC-003 建 code 任务被拒 `商务闸门未通过：SC-003 未完成商务审查` | 可用，但会把没合同的新项目锁死 |
| 新项目无报价 | `gate finance check SC-999` 报 `[阻断] 毛利率：无报价单`、`[阻断] 预付比例：无合同` | 按设计拦截 |
| 商务闸门与开票 | 闸门确认时开票信息只是警告；开票时才阻断 | 两段式摩擦，但提示清晰 |

### 6.3 验收命令机制

**能写、能执行：**
```text
$ python3 agency.py task add ... --done-when "cmd: test -s clients/SC-004-一人公司经营/05-验收清单.md"
已建 T-0146

$ python3 agency.py task close T-0146 --evidence "验收清单存在，cmd 机制生效"
已关闭 T-0146（done），验收通过。
证据：验收清单存在，cmd 机制生效｜验收: test -s clients/SC-004-一人公司经营/05-验收清单.md｜exit 0｜
```
`cmd:` 前缀、`--verify` 覆盖、`shell=True`、`cwd=ROOT`、600s 超时、退出码非 0 拒绝关闭，均实测有效。

**但有三个坑：**
1. **建单强制 `done_when`，验收标准却常常后补。** 不带 `--done-when` 直接 argparse 报错（`S1-39`）。
2. **`test -s` 配 glob，重跑后多文件会报错。** 复制出第二个 `*-planner-T-0127.md` 后：
   ```text
   $ bash -c 'test -s agency/outputs/*-planner-T-0127.md'
   bash: line 0: test: agency/outputs/20261113-015919-planner-T-0127.md: binary operator expected
   EXIT:2
   ```
   任务会被拒绝关闭，即使两个文件都存在。`grep -q` 可以处理多文件，`test -s` 不行。
3. **弱命令能通过空模板。** `test -s clients/SC-001-.../04-项目计划.md` 对 `project init` 生成的模板返回 0（`S1b-05`）。

### 6.4 快照上的自检红灯

```text
$ python3 agency.py doctor
[错误] 测试: 306/308 通过，失败 2，错误 0
FAIL: test_start_gate_alone_rejects_code_task
  AssertionError: '商务闸门未通过' not found in 'None'
FAIL: test_code_task_requires_finance_gate
  AssertionError: '已建' not found in '已存在 T-0001（内容幂等，未重复建单）｜测试任务'
自检结果: 有问题
EXIT:1
```
两个失败同源：测试在临时库上运行，`finance_gate_mode()` 取默认 `warn`，于是 code 任务被放行；测试预期是 `block`。快照期间另一条线仍在改 `agency.py`（214KB → 231KB），这两个失败可能是进行中的改动，但“默认 warn 与测试/文档预期 block 不一致”在快照代码里可直接复核。

## 8. 接真客户前必须先修（按顺序）

1. **P0-01 跨项目任务去重**：去重键加入 `project`；跨项目同名只提示，不得返回别的项目任务。否则客户 A 的活会被客户 B 吞掉。
2. **P0-02 多项目 WBS/指标口径**：`stats`/`brief`/`finance summary` 加项目维度；`check_consistency` 按项目分线并给新项目字段默认值；`sync_plan` 不得只查 OPC-002 固定范围。否则“完成率”和“四处一致”都是假数。
3. **P0-03 闸门语义统一**：明确 `warn`/`block` 下 `task add` 与 `plan` 的行为必须一致；默认值与 `doctor`/测试对齐，先把自检恢复绿灯。否则同一动作两个结果，无法向客户解释。
4. **P0-04 稠密检索补全局资产**：`_matrix(project)` 必须包含 `project_id IS NULL` 的 `company/`、`templates/`；或在 dense 结果后强制补全局检索。否则客户项目一多，Agent 反而越来越“不懂公司套路”。
5. **P0-05 建单/验收解耦**：允许 `done_when` 先占位，关单前强制补可执行命令；不要在建单时用 argparse 硬卡。否则真实接单节奏走不动。
6. **P0-06 商务单据链**：合同必须关联同项目报价（或明确“无报价合同”审批），校验金额/客户一致；否则闸门形同虚设。
7. **P1-07/P1-14 验收命令质量**：验收模板改成内容级检查（如 `grep` 必填章节），文档不要推荐 `test -s glob`；init 模板加“未填写”标记，防止假验收。
8. **P1-08 变更单**：至少提供“变更记录”实体，能关联合同、金额、范围与验收；否则范围蔓延无法计费。
9. **P1-09 项目维度统计**：`task stats --project`、`finance summary --project` 必须先有，否则多客户经营是盲的。
10. **P1-10/P1-12/P1-13**：依赖编号、时区显示、默认计划窗口，属于“接第一个真客户就会天天遇到”的低成本高收益修复。
