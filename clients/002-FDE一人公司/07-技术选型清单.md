# 07 技术选型清单

- 版本：v1
- 更新：2026-11-11
- 原则：P0 只用标准库 + SQLite；每引入一个组件，迁移包就重一分，别人就多一个装不上的理由。

---

## 1. Agent 框架与编排

| 技术 | P0 | 理由 | 何时再评估 |
|---|---|---|---|
| LangChain | 不用 | 抽象层厚、调试难、版本变动大；我们只需拼提示词 + 单次调用 | 需要接 10+ 工具或大量模型差异适配时 |
| LlamaIndex | 不用 | 面向 RAG 与数据接入，P0 无知识库场景 | 首单为知识库问答时 |
| LangGraph | 不用 | 见 ADR-001，事件驱动用不上固定图 | 分支 ≥5、需可视化回放 |
| CrewAI | 不用 | 角色对话式协作，与我们看板模型冲突，成本与可控性差 | 不做 |
| AutoGen | 不用 | 同上，多智能体对话难审计 | 不做 |

## 2. 可观测与评测

| 技术 | P0 | 理由 | 何时再评估 |
|---|---|---|---|
| LangSmith | 不用 | SaaS，数据出境，客户敏感场景不可用 | 自托管可选项出现时 |
| Langfuse | P1 首选 | 自托管、可看 trace 与成本；但需 Docker + Postgres | 角色 >15 或需 trace 对比 |
| Promptfoo | P1 首选 | 评测用例与断言成熟，适合做回归；需 Node 环境 | 用例 >30 条或需模型 A/B |
| Braintrust | 不用 | 企业级 SaaS，成本与合规不匹配 | 不做 |
| Arize | 不用 | 偏 ML 监控平台，过重 | 不做 |

## 3. 向量与检索

| 技术 | P0 | 理由 | 何时再评估 |
|---|---|---|---|
| Milvus | 不用 | 分布式部署，单人无运维必要 | 单库 >500 万条 |
| Pinecone | 不用 | SaaS 付费 + 数据出境 | 不做 |
| Chroma | P1 可选 | 嵌入式、依赖轻，适合单机知识库 | 首单知识库场景 |
| pgvector | P1/P2 推荐 | 客户已有 Postgres 时最省事 | 客户有现成 PG |
| SQLite 自建检索 | P0 采用 | 10 万条内暴力检索足够，零依赖 | 数据量超阈值再换 |

## 4. 数据与流程编排

| 技术 | P0 | 理由 | 何时再评估 |
|---|---|---|---|
| dbt | 不用 | 面向数仓建模，我们是交付方不是数据团队 | 客户 BI/数仓项目 |
| Airflow | 不用 | 需调度服务与元数据库，过重 | 跨系统长任务 >10 条 |
| Prefect | 不用 | 比 Airflow 轻，但仍需服务端 | P1 跨机器编排时评估本地模式 |

---

## 5. 场景到技术的映射

| 首单场景 | 引入 |
|---|---|
| 知识库问答 | Chroma 或 pgvector + 自建检索 |
| 固定审批流 | LangGraph（仅该条流程） |
| 多模型对比评测 | Promptfoo |
| 需要 trace 复盘 | Langfuse（自托管） |
| 客户有数仓 | dbt + pgvector |

## 6. 判断标准

引入一个新组件，必须同时满足：

1. 解决 P0 绕不过的问题，而不是"以后可能用得上"
2. 不增加迁移步骤，或增加不超过 1 步
3. 有明确替换触发条件，写进本清单
