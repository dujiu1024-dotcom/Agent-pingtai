# 06 技术方案

- 版本：v1
- 更新：2026-11-11
- 状态：待确认
- 原则：单人可维护、单文件可迁移、无外部服务依赖（飞书与模型除外）

---

## 1. 选型与理由

| 项 | 选择 | 理由 |
|---|---|---|
| 语言 | Python 3.11+，仅标准库 | 零依赖，换机不用装环境 |
| 存储 | SQLite 单文件 | 事务安全、可备份、迁移就是拷文件 |
| 交互 | 命令行 | 单人使用，最快；网页留 P1 |
| 模型 | OpenAI 兼容接口 | 商汤可换任意厂商，不锁定 |
| 文档 | 本地 Markdown + 飞书镜像 | 本地可版本化，飞书可协作 |
| 调度 | 手动 `tick` 或 launchd 每 5 分钟 | 不做常驻服务，降低故障面 |

明确不引入：ORM、Web 框架、消息队列、Redis、Docker。

## 3. 数据模型

```sql
projects(id, name, status, created_at, confirmed_at)
tasks(id, project_id, title, owner, status, start_at, due_at,
      done_when, evidence, blocked_reason, created_at, closed_at)
events(id, type, task_id, payload, dedup_key, created_at, delivered_at)
facts(id, project_id, content, source_level, source_ref, created_at)
reminders(id, task_id, kind, scheduled_at, sent_at, count)
agent_runs(id, role, task_id, model, prompt_hash, output_path,
           tokens_in, tokens_out, created_at)
docs(id, local_path, node_token, content_hash, synced_at, state)
config_kv(key, value)
dead_letter(id, event_id, role, error, attempts, created_at)
```

约束：
- `tasks.status` 仅允许 `todo/doing/blocked/review/done/closed`
- 关闭必须有 `evidence`，否则拒绝
- `events.dedup_key` 唯一，防重复提醒
- `facts.source_level` 仅 S1-S4，S4 不得进入对外文档

## 4. 事件引擎

每 5 分钟或手动 `tick` 执行：

1. 扫描任务：距开始 ≤1 天、距截止 ≤2 天、已逾期。
2. 生成事件，按 `dedup_key = type + task_id + date` 去重。
3. 过滤时段：09:00–23:00 直接推送；否则入队。
4. 同任务当日推送 ≥3 次则生成升级事件给幕僚长。
5. 逾期 ≥3 天且无更新，标记 `blocked` 并要求写原因。

事件类型：`task_created / task_due_soon / task_overdue / task_blocked / milestone_hit / gate_blocked / sync_conflict`。

---

## 5. 任务状态机与闸门

```
todo → doing → review → done → closed
         ↘ blocked ↗
```

- 进入 `doing` 前校验五要素（动作、owner、截止、完成标准、证据要求）。
- `closed` 必须由秘书写入证据摘要。
- 代码类任务额外校验项目存在有效确认单，否则拒绝创建。

## 6. Agent 运行时

- 角色文件 `ROLE.md` 作为系统提示主干。
- 注入上下文：项目事实（按 S1→S3 排序）、相关任务、当前缺口。
- 模型路由：`AGENCY_MODEL` 默认 `deepseek-v4-flash`；支持按角色覆盖。
- 稳定性：429 退避重试 3 次；`reasoning_effort` 不支持时降级 `low`；超时 180 秒。
- 成本：记录 tokens，按日汇总；单日超阈值告警。
- 产出：写 `agency/outputs/<时间>-<角色>-<任务>.md`，同时登记 `agent_runs`。

## 6.1 协作模型：不对话，走看板

**Agent 之间不直接对话。** 没有"角色 A 问角色 B、B 回答"的链路。

本质是**黑板模型 + 订阅规则**：所有角色读写同一块看板，由"事件类型 → 角色"的声明式规则决定谁被唤醒。流程不写在代码的图里，而写在数据里。

协作只通过三条通道：

| 通道 | 载体 | 说明 |
|---|---|---|
| 状态 | `tasks` 表 | 谁负责、到哪一步、卡在谁那里，一眼可见 |
| 事件 | `events` 表 | 状态变化产生事件，订阅该事件的角色被唤醒 |
| 产物 | 文件 + `docs` 表 | 交接物是文档，不是聊天记录 |

**交接靠卡点，不靠打招呼**：

```
产品经理产出《确认单》→ 项目状态 confirmed
        ↓ 触发 event: project_confirmed
规划师被唤醒 → 读确认单 + 事实台账 → 产出 WBS 任务
        ↓ 触发 event: tasks_created
秘书被唤醒 → 校验五要素 → 排期 → 临期提醒
        ↓ 触发 event: task_coding
教练被唤醒 → 出指南与考题
```

**缺信息时**：Agent 不允许去问另一个 Agent，只能产出一个"待补信息"事件，进你的待办队列。

**为什么不做直接对话**：会形成循环调用、责任模糊、成本不可控、无法审计。单人公司的事件量，用数据库做总线最便宜。

## 6.2 无人值守分级

| 级别 | 范围 | 是否可无人 |
|---|---|---|
| L0 巡检 | tick 扫描、生成提醒、跑评测、检查同步 | 可以 |
| L1 起草 | 简报、诊断初稿、WBS 草案、周报、内容草稿 | 可以，产出进待审队列 |
| L2 对外 | 发送客户、报价、签约、关闭任务、发布内容 | 必须人工确认 |
| L3 资金 | 收付款、合同变更 | 仅你执行 |

**无人值守的六个前提**（缺一不可）：

1. 幂等：同一事件重复触发，结果不变
2. 去重：`dedup_key` 防重复提醒
3. 超时：单次调用 180 秒，超时记失败，不挂死
4. 熔断：同一角色连续失败 3 次，暂停并告警
5. 成本闸：单日 token 上限，超限停止自动调用
6. 死信：失败任务进 `dead_letter` 表，不静默丢弃

调度方式：launchd 每 5 分钟执行 `tick`；23:00–09:00 只入队不推送。

**能力边界**：P0 能做到 L0、L1 无人值守；L2 永远需要你点确认。"完全无人"不做承诺。

## 6.3 提醒通道：双身份分工

**定位**：机器人是 Agent 的嘴巴和耳朵——任务增删改、提醒消息、卡片按钮、无人值守。文档读写归用户身份，因为文档权限只能跟着人走。

**分工表**：

| 身份 | 承担 | 不承担 | 理由 |
|---|---|---|---|
| 机器人（tenant_access_token） | 任务增删改、提醒推送、卡片按钮回调、事件订阅 | 文档与 wiki 读写 | 凭据长期有效，夜间无人值守不会因 token 过期停机；但个人知识库默认对它不可见，逐个节点授权是长期维护成本 |
| 用户（user_access_token） | 文档创建/更新、wiki 节点、知识库同步 | 主动发起会话 | 文档权限跟人走，无需额外授权；但 token 会过期，不适合无人值守 |

**通道优先级**：

| 通道 | 身份 | 阶段 |
|---|---|---|
| 飞书任务 | 机器人 | P0 主通道 |
| 机器人单聊消息 / 卡片 | 机器人 | P0 提醒，P1 交互 |
| 飞书文档 | 用户 | P0 |
| 终端输出 | — | 兜底 |

**凭据约束**：`app_id` / `app_secret` 只进 `.env`（600 权限），不写文档、不进 git、不进飞书。泄露即等于整个租户的 im/task 能力暴露，比用户 token 风险更高，轮换成本也更高。

**计划源不变**：SQLite 是唯一事实源，飞书任务是映射与提醒载体，不反向作为计划源。理由：平台要卖给别人，不能绑死在飞书上。

**tick 流程**：

```
读 SQLite 待提醒任务
  → 按 dedup_key 创建/更新飞书任务（标题、开始、截止、负责人、描述）
  → 读回飞书任务的完成状态
  → 回写 SQLite（只同步"完成/未完成"）
  → 生成提醒事件，写 agent_runs
```

**映射表**：

```
feishu_tasks(local_task_id, feishu_guid, identity, last_synced_at, sync_status)
```

`identity` 取值 `bot` / `user`，用于定位是哪套凭据写的，排障时不至于查错账号。

**字段映射**：

| SQLite | 飞书任务 |
|---|---|
| title | summary |
| start_at | start.timestamp |
| due_at | due.timestamp |
| owner | members |
| notes + 编号 | description |
| status=done | completed_at |

**约束**：23:00–09:00 不创建、不推送；同一任务一天最多提醒 1 次；飞书侧被删除的任务，本地标 `sync_lost` 并进待办。

## 7. 审计引擎

三条可自动化的规则：

1. **日期**：产出中的日期必须在输入事实中出现，否则标记。
2. **来源**：引用 S1/S2 的条目，必须能在 `facts` 表找到对应记录。
3. **假设**：出现"据了解、通常、普遍、大概"等词且无 S4 标记，判定违规。

审计结果写事件；对外文档存在未处理标记时，禁止推送飞书。

## 8. 飞书同步

- 本地为主库，飞书为镜像。
- `docs` 表记录 `content_hash`，推送前比对，未变更不重复写。
- 推送后回写 `synced_at`。
- 拉取时若远端哈希与本地记录不一致，标记 `sync_conflict`，不自动覆盖。
- 密钥、密级 L3/L4 内容永不同步正文，只同步索引。

## 14. 架构决策记录（ADR）

### ADR-001 不引入 LangGraph（2026-11-11）

**决定**：P0 用"角色文件 + 单次调用 + 状态机"实现编排，不引入 LangGraph。

**理由**：
1. 我们的流程是事件驱动，不是固定图。任务从创建到关闭由状态机推进，多角色并发少、分支浅，图框架的主要价值用不上。
2. LangGraph 会带来依赖链、版本升级和调试成本，与"单文件可迁移、零依赖"直接冲突。
3. 6 天工期下，学习与调试成本高于收益。

**重审触发条件（满足任一）**：
- 同时在建项目 ≥3 个，需要跨项目编排
- 单条流程分支 ≥5 个，状态机难以表达
- 需要可视化回放、断点续跑、人工介入编排
- 要把编排界面作为卖点对外销售

**保留接口**：编排收敛在 `orchestrator` 层，角色调用只暴露 `run(role, context)`，将来替换实现不影响上层。

---

### ADR-002 引入最小评测 Harness（2026-11-11）

**决定**：P0 做最小评测集，不引入第三方评测框架。

**组成**：
- 20 条黄金用例：角色 × 任务类型，输入固定，期望输出结构固定
- 3 个指标：结构合规率、无来源日期数、S1/S2 引用可追溯率
- 回归基线：每次改提示词或换模型，跑一遍，指标不得低于基线

**理由**：模型行为不稳定已被验证（lite 模型编造 4 处事实）。没有回归评测，换模型就是盲换。

**成本**：约 4 小时，放在 11-15，与审计模块同日完成。

---

### ADR-003 不做 Agent 间直接对话（2026-11-11）

**决定**：协作走共享状态 + 事件总线 + 产物交接，角色之间不互相调用。

**理由**：直接对话会产生循环调用、责任归属模糊、token 成本不可控、审计困难。事件驱动的看板模型可回放、可追责、可降级。

**代价**：交接有延迟（一个 tick 周期），复杂协商场景表达力弱。

**重审条件**：出现必须多轮协商才能决策的场景（如多方报价博弈），改为人在环路中主持，仍不做自动对话。

---

### ADR-004 工作记忆结构化、向量记忆进 P0（2026-11-11）

**决定**：
1. 工作记忆落 `wm_session` 表，按固定槽位组装，可恢复、可压缩，不做字符串拼接。
2. P0 自建 `embeddings` 表 + 暴力余弦检索，嵌入优先本地 Ollama，兜底 hash-tfidf。
3. 两者通过 `VectorStore` 与 `Memory` 接口隔离，P1 换 Chroma/pgvector 不改上层。

**理由**：上下文与检索是后续所有能力的地基。P0 先用简易实现占位，后补会牵动全部提示词与数据结构，返工成本高于现在多做的 10 小时。

**代价**：占用 16 小时缓冲中的 10 小时，剩余 6 小时。

**重审条件**：嵌入质量不达标（召回准确率 <60%）时，只保留候选召回用途，不用于自动决策。

---

### ADR-005 飞书接入采用双身份分工（2026-11-11）

**决定**：建企业自建应用（机器人），承担任务增删改、提醒推送、卡片按钮回调与事件订阅；文档与 wiki 读写继续用用户身份。

**理由**：
1. 机器人凭据（app_id/secret）长期有效，夜间无人值守不会因 token 过期停机；用户 token 约 30 天需重新登录，是无人值守的单点故障。
2. 机器人是 Agent 唯一的主动出口——没有它就只能等你来问，做不了"到点提醒"和"点按钮确认"。
3. 但机器人对个人知识库默认不可见，让它读文档就要逐个节点授权，节点越多维护成本越高。文档交给用户身份，零授权成本。

**代价**：
- 多一套凭据要保管，且泄露影响面大于用户 token。
- 权限变更、事件订阅调整需要发版审核。

**边界**：机器人不申请任何文档类权限（`docx:*`、`wiki:*`），只申请 `task:*`、`im:*`。申请了却不用，等于白白扩大攻击面。

**重审条件**：若需要机器人代读客户文档（例如做外部交付时），再单独评估该客户的文档授权方式，不默认放开。

## 16. 主要风险

| 风险 | 应对 |
|---|---|
| 模型指令跟随不稳 | 提示词固定结构 + 输出审计 + 换模型 |
| 飞书同步冲突 | 哈希比对，冲突不覆盖 |
| 6 天不够 | 砍网页、砍自动调度，保 CLI 与迁移 |
| 单人维护成本 | 仅标准库，禁止引入框架 |
