## 4. 工作记忆六槽位

```bash
python3 agency.py memory set T-0011 pm --slot constraints \
  --text "问卷必须与 templates/客户诊断问卷.md v1.0 对齐，含计分口径，不要另起一版" \
  --source "创始人 2026-11-12 口头"
python3 agency.py memory show T-0011 pm
```

```
【目标】诊断包定稿（问卷/访谈提纲/报告/报价单）
【约束】
- 问卷必须与 templates/客户诊断问卷.md v1.0 对齐，含计分口径，不要另起一版 ［创始人 2026-11-12 口头 2026-11-12］
【未决问题】
- 报价单模板是否按 2 小时出方案的标准改？（longyi） ［T-0011 计划评审 2026-11-12］
【最近产物】
- # 诊断包定稿（OPC-002 / T-0011） ［agency/outputs/20261112-135123-pm-T-0011.md 2026-11-12］
【历史摘要】第一轮产出是新造问卷，未对齐仓库现有模板，被判定返工

轮次 1｜累计 token 3866｜更新 2026-11-12T05:52:55+00:00
```

- 四个槽位写入均成功；无 `--source` 的写入会被拒绝（代码层强制）。
- 渲染顺序固定，超预算会按 digest → artifacts → constraints 顺序裁剪，goal 与 open_questions 不裁。
- **效果可验证**：写入约束后重跑 pm，第二轮不再重造问卷，改为"直接引用 v1.0，不做任何改动"，并把报价单列为未决问题。

判定：**六槽位是真的，且是这套平台里性价比最高的机制之一**——一次 `memory set` 抵十行 prompt。

## 6. 事件总线与 sync

```bash
python3 agency.py sync
```
```
[投递] #106 task_created → secretary:notify｜约 0 tokens
[归档] #107 task_closed｜无启用订阅，标记已投递
...
[失败] #118 audit_flag → auditor:run｜LLM 调用失败：限流：{"error":{"message":"inference exceeds tpm/rpm limit",...}}
[投递] #120 audit_flag → auditor:run｜约 2474 tokens
[投递] #124 audit_flag → auditor:run｜约 2640 tokens
[投递] #126 audit_flag → auditor:run｜约 2548 tokens
本轮：待投递 26，成功 12，失败 1，无订阅归档 13。
```

耗时 **55.58s**（因为同步触发了 3 次 LLM）。

问题很明确：`audit_flag` 的 3 次自动审计，全部源自**审计器的日期误报**：

```
审计：发现 4 处疑似无来源信息，需人工核实：
  - 日期 0-5 未出现在输入事实中
  - 日期 5-15 未出现在输入事实中
  - 日期 15-25 未出现在输入事实中
  - 日期 25-30 未出现在输入事实中
```

`0-5`、`5-15` 是"0-5 分钟""5-15 分钟"的时间区间，被正则 `\d{1,2}-\d{1,2}` 当成月-日。于是：**误报 → 事件 → 订阅 → 自动烧 token 审计**，约 7,600 token 换回三份"审计通过"。

判定：事件总线**机制是真的**（26 条事件、订阅匹配、失败单独计数都对），但默认订阅配置在给误报买单。

### 11.10 `insufficient_quota` 的真实原因与三级降级

**先纠错**：之前把 `insufficient_quota` 读成"账户余额不足"，是错的。创始人后台显示 5 小时可用率 99.8%、周余额 109 万，余额根本没动。

**排查（同一 key、同一 base_url，只改请求内容）**

| 测试 | 结果 |
|---|---|
| `GET /models` 8 个模型 | 全部标 `tokenplan` + `metered`，plan 覆盖没有差别 |
| 8 个模型各发 1 次 `"hi"`（max_tokens=4） | 多数 200；`glm-5.3` / `kimi-k3` 间歇 429 `EndpointTPMExceeded`；`deepseek-flash` 429 `EndpointRPMExceeded` |
| `sensenova-u1.5-lite` | 两次都 404 `model is not found`（列表里有，实际不可用） |
| `deepseek-v4-flash` 逐档加大 prompt | 0.6k/2k/4k 字符 → 200（最大 2,941 prompt tokens）；8k 字符 → 429 `rpm exhausted` |
| 用 ~5k token 的真实规模 prompt 连发 3 次 | 3 次全 429 `insufficient_quota` |
| **等待 65 秒后发同一条 5k prompt** | **200 通过** |

**结论**：不是余额、不是 plan 不覆盖、不是 key 分组缺权限。是**供应商按分钟窗口算的 endpoint TPM/RPM 限流**，把 `inference exceeds tpm/rpm limit` 塞进了 `code=insufficient_quota` 这个误导性字段里。我们真实派活的提示词 2.5k~5k token，刚好压在阈值附近，于是"有时成功、有时 insufficient_quota"。65 秒恢复证明它是**瞬时错误**，不是永久错误。

**据此分三级**（`agency.py` + `console.py`，约 70 行）：

1. **同模型退避一次**（`AGENCY_LLM_BACKOFF`，默认 5s）——限流是窗口级，等一会就可能恢复；
2. **换 endpoint 降级**（`AGENCY_MODELS="a,b,c"`）——同一时刻 A 429 而 B 200 是观察到的现象；但 11.11 的实测推翻了"各模型配额独立"的说法：只有 Flash-Lite 池独立，通用池内模型会互相挤占，降级顺序须按池子排；
3. **进重试队列**（`AGENCY_RETRY_MAX`/`AGENCY_RETRY_BASE`，默认 2 次、60s 起指数退避）——候选全部限流时，控制台任务挂"排队重试"，页面可见。

永久错误不重试：`model is not found` / 401 / 403 / invalid_api_key 直接判失败并降级到下一个模型。

**验证（打桩服务 + 真实请求）**

| 场景 | 结果 |
|---|---|
| 主模型 404 `model is not found` | 无退避，直接 `[降级] bad-model 不可用（unavailable），切到 ok-model`，成功 |
| 主模型 429 `rpm exhausted` | `[退避] rl-model 触发限流，1.0s 后同模型再试一次` → 仍 429 → `[降级] …（rate_limit）` → 成功 |
| 全部候选 429 | 任务 `retrying`，20s → 40s 两轮后置 `failed`；页面卡片显示 `R-0001 · 后台执行 排队重试 120s` |
| 真实链路（`.env` 配 `deepseek-v4-flash,glm-5.2`） | 一次通过，`agent_runs.model=deepseek-v4-flash` |

新增 `tests/test_state.py::LLMErrorClassTest` 4 条锁住分级；全量 212 → **216/216 通过**。

**给创始人的运维结论**：把 `AGENCY_MODELS` 配成**不同厂商/不同 endpoint** 的模型，才有真正的降级意义（同 endpoint 会共享配额）。`sensenova-u1.5-lite` 虽在目录里但不可调用，别放候选首位。

### 11.11 token plan 边界实测 + 按 endpoint 限流

**探测方式**：递进式，每步记录真实 `prompt_tokens`，遇 429 即停该维度（不猛刷）。共消耗约 27 万 token，其中 flash-lite 约 22 万。

**边界表（2026-11-12 实测）**

| 模型 | 可调用 | 单请求安全上限 | TPM | RPM | 并发安全值 | 限流恢复 | 证据 |
|---|---|---|---|---|---|---|---|
| `sensenova-6.8-flash-lite` | 是 | 32k（实测 48k prompt 仍 200） | ≥18k | ≥60 | **4** | 60s | 2k×6 间隔 1s 全 200；并发 4 全 200，并发 8 出现 3/8 429；24k/48k 单请求 200 |
| `glm-5.2` | 是 | 24k | ~10k | ~10 | 2 | 60s | 24k prompt 200；36k 级请求 429 `rpm exhausted` |
| `deepseek-v4-flash` | 是（实际近乎不可用） | 6k | ~4k | ~4 | 1 | 60s | 冷却 180s 后首次 200、其后 2k 请求 10s 间隔仍 429；5k prompt 连发 3 次全 429 |
| `sensenova-6.8-flash` | 是 | 8k（未单独压边界，取保守默认） | 6k | 6 | 2 | 60s | 小请求多次 200 |
| `sensenova-u1.5-lite` | **否** | — | — | — | — | — | 两次均 404 `model is not found` |

**两个池子得到证实**：deepseek 429 的同一分钟内，flash-lite 仍 200（24k、48k prompt 都通）——对应后台的「Flash-Lite 专属积分池」。而 deepseek 与 glm-5.2 在高负载时会一起 429，说明二者共享「通用池」。**11.10 里"各 endpoint 配额独立"的说法不准确**：只有 Flash-Lite 池是独立的，通用池里的模型互相挤占。

**结论排序**：主模型用 `sensenova-6.8-flash-lite`（独立池 + 高上限），降级到 `glm-5.2`，最后才是 `deepseek-v4-flash`。`.env` 已按此顺序配置。

**写进程序（`ratelimit.py` + `agency/limits.json`，约 120 行）**

1. **按 endpoint 分桶**：每模型一个 (token 预算, 请求数) 的 60s 滑动窗口；发送前用 `estimate_tokens()`（中文 1.5 字/token）预估，超预算就**在本地排队等窗口**，并打印 `[限流] X 本分钟预算不足，等待 Ns 后再发`，不再硬打出去；
2. **并发闸门**：进程内每模型一个信号量（flash-lite=4），控制台再加一层 `MAX_PARALLEL=4`，超了直接拒绝并说明"达到实测安全并发"；
3. **参数来自实测**：`limits.json` 存每个模型的 max_prompt_tokens/tpm/rpm/concurrency/recovery，退避起点从 5s 改为实测的 60s（`AGENCY_LLM_BACKOFF`、`AGENCY_RETRY_BASE`）；
4. **超长提示词给明确提示**：预估超过单模型上限直接报
   `提示词约 2989 token，超过 sensenova-6.8-flash-lite 单请求上限 500，请拆分任务后再跑`（用临时 limits 文件验证，未发出网络请求）；
5. `model_candidates()` 过滤 `callable=false`，`sensenova-u1.5-lite` 不会再进候选。

**验证**：连续两次真实派活（content / T-0029），429 零次，`agent_runs` 记录 `model=sensenova-6.8-flash-lite`，各 9s 内完成；`doctor` 222/222（新增 `tests/test_ratelimit.py` 6 条）。

### 11.12 黑板模型核查：没有落地，角色是各干各的

**设计说的是**：Agent 之间通过共享看板 + 事件驱动协作。

**代码里实际是**（`build_prompt` 四段固定顺序，`agency.py#L1634`）：

```
【事实】ROLE.md + 公司宪法 + facts 表(本项目 8 条) + 向量检索(5~8 条)
【任务】任务 JSON + 未关闭任务列表
【记忆】wm.render(task, role) —— 只有这个 (task, role) 自己的六槽位
【指令】输出要求
```

- 其他角色的产出（`agency/outputs/*.md`）**没有任何读取路径**：没有代码扫描 outputs，也没有把别人的产出写进提示词；
- 决策（`decisions` 槽位）按 `(task_id, role)` 隔离：`wm_session` 13 行里，T-0011 只有 `pm` 有内容（digest 115、artifacts 928、decisions 111），`auditor` 同任务下只有自己上一次的审计结论；
- 事件表**只做投递，不携带内容**：`_dispatch_execute(role, task)` 只把任务对象给被唤醒者，事件的 `payload/detail`（"为什么叫醒你"）不进提示词；
- 真正共享的只有两层：`facts`（人工录入，全项目可见）和向量索引（docs/templates），所以角色能引用同一份模板，但引用不到同事的结论。

**实测证据**：给 `auditor`（T-0011）构造真实提示词，7,790 字里
```

含「pm 的结论」：False
含「产出文件」：False
含「按结果定价」：True   ← 来自 templates 向量检索，不是来自 pm
```
它的【记忆】段只有一行：`【审计结论】整改后通过［agency/outputs/…-auditor-T-0011.md］`。

**事件在协作中的真实作用**（库内现状）：
```
events 总数 112，未投递 25
订阅 7 条，其中 enabled=0 的 5 条：
  task_created→secretary notify(1)、task_due_soon→secretary notify(1)、
  task_overdue→secretary notify(1)、audit_flag→auditor run(1)、其余 run 全关
```
即：事件目前只当"变更通知"用（给秘书发提醒），没有形成"谁产出→谁接棒"的内容流通。`audit_flag→auditor run` 是唯一在跑的自动唤醒，也正是 11.4 里误报连锁（约 7,600 token）的来源。

**缺口与影响**

| 缺口 | 现实影响 |
