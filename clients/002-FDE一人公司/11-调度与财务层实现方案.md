
## 8. P2 追加：飞书直调（T-0021）

### 8.1 指令路由

飞书不再只是出站通知：`listener.py` 收到消息后先交给 `feishu_commands.py` 解析，命中指令就异步执行并回发结果；普通消息仍只回执并留档 `inbound.jsonl`。

| 指令 | 行为 |
|---|---|
| `/help` | 返回指令说明，不执行任何子进程 |
| `/brief` | 调 `agency.py brief`，回一页态势 |
| `/sync [--force]` | 调 `agency.py sync`，`--force` 忽略 09:00–23:00 时段 |
| `/run <角色> [任务ID] [附加指令]` | 调 `agency.py run`，任务 ID 须形如 `T-0001`，其余词作为 `--note` |

边界与约束：
- **执行路径不变**：一律 `agency.py` 子进程，与 CLI、控制台同源；不新增第三条执行链，不绕过开工/商务闸门。
- **白名单**：`FEISHU_ALLOWED_OPEN_IDS`（逗号分隔），缺省只认 `FEISHU_USER_OPEN_ID`；未配置时拒绝所有指令并回发 open_id 供填写；非白名单用户被拒。
- **回发约束**：单条回复截断到 2500 字（保留末尾），`/run` 先回「收到，开始执行……」避免长时间无响应。
- **不做的部分**：仍不解析自然语言为任务，也不把消息入库生成任务——那是 T-0020 的 20.3。

验收：16 条 `tests/test_feishu_commands.py` 通过；陌生人指令被拒；`/run planner T-0019 只做 19.3` 能组装出 `run planner --task T-0019 --note 只做 19.3`。

**现在只做两件零成本的事**（并入 T-0016）：实体 ID 规范（`proj:` / `task:` / `role:` / `doc:` / `client:`），以及输出文件 front-matter。这两项不做，未来抽取必须回溯改历史数据。

## 10. 明确不做

- 图数据库、知识图谱可视化界面（数据量不足，延后）
- 对接税务 / 发票系统
- 全自动无人值守：L2 对外、L3 资金永远人工
- Agent 之间互相对话（坚持黑板模型）
- 事件订阅默认自动调用 Agent（默认关闭）

## 11. 总验收

| # | 验收项 | 判定 |
|---|---|---|
| 1 | 本体一致性 | ontology 与 `EVENT_TYPE` 差集为空 |
| 2 | 财务闭环 | 报价→合同→开票→回款全链路可查 |
| 3 | 闸门有效 | 未过商务闸门的 code 任务被拒 |
| 4 | 调度可用 | `plan` 草案合规入库；`dispatch` 超预算能停 |
| 5 | 事件闭环 | 积压事件清零，重复 sync 不重投 |
| 6 | 不破 P0 | `check_consistency` 四方仍为 90h |
| 7 | 飞书直调 | 白名单外拒绝；`/run` 参数组装正确；`test_feishu_commands` 16 条通过 |

## 12. 风险与回滚

| 风险 | 应对 |
|---|---|
| 枚举扩展导致旧事件写入失败 | 迁移只增不删；先备份 `agency.db` |
| 商务闸门过严挡住正常单 | 阈值写进 `config_kv`，可现场调整 |
| 事件总线误触发烧 token | 默认全关 Agent 类订阅；单订阅预算上限 |
| 调度误关任务 | 调度层无关闭权限，关闭只走人工+证据 |

每个阶段的数据库变更均先备份，失败可按 `tools/migrate_fields.py --restore` 还原。

## 13. 修订规则

1. 本文件随实现进展更新，版本号递增。
2. 计划或日期变动，同一轮同步：`agency.db`、04、09、飞书两张表，并回读核验。
3. 本方案属 P1，任何改动不得影响 P0 的 90h 口径。
