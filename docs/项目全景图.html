一份用大白话讲明白的项目全貌。五张图分别回答五个问题： 业务流程图讲"事情怎么一步步做"， 业务架构图讲"谁干什么、谁管谁"， 技术架构图讲"用了什么技术、模块怎么拼"， 技术流程图讲"一条命令进去、内部怎么跑一圈出来"， 数据流程图讲"数据从哪来、存哪、给谁用"。

图 1 · 业务流程图（事情怎么一步步做）

一句话总结：客户找上门 → PM 聊清楚需求写方案 → 客户点头 → Planner 拆任务排期 → 秘书盯进度到点催 → 各个 Agent 按分工干活 → Auditor 查质量 → 交付 → Finance 要钱。 下面这条线就是从"客户来咨询"到"钱进账"的完整旅程，每个节点是谁的事、卡在哪一关不能往下走，一目了然。

图 2 · 业务架构图（谁干什么、谁管谁）

一句话总结：整个工作室就是 11 个 AI Agent，每个角色只干自己那份活、有明确的上下游和输入输出。 分三层看——顶层是两个总管（参谋长拍板、审计查账），中层是产品线的主角（PM→Planner→Secretary 这一条铁三角）， 底层是执行层（content、scout、producer 等干具体活的），侧边是支撑角色（HR 管 Agent 人事、Finance 管钱）。 箭头指向 = 谁给谁派活 / 谁给谁产物。

图 3 · 技术架构图（用了什么技术、模块怎么拼）

一句话总结：当前是 "两条线并行"——老线（单文件 CLI + SQLite）稳定跑着，新线（agent_platform/）在并行建设， 未来逐步替换。新架构从上到下五层，但编排层有两个兄弟组件不是一个： 入口层（CLI/控制台/API）→ 控制面（身份、配额、审计）→ 编排层（LangGraph 管"步骤顺序" + Hybrid Blackboard 管"跨 Agent 共享认知"，分工不同、并行协作）→ 运行时（Agent 执行引擎 + 工具网关）→ 存储层（PostgreSQL 是唯一事实源、Redis Streams 只做事件唤醒、pgvector 做语义检索）。 所有外部调用必须经过工具网关，Agent 不能直接碰任何外部东西。

图 4 · 技术流程图（一条命令进去，内部怎么跑一圈出来）

一句话总结：以"PM 写方案 → Planner 拆任务"为例。老架构就是一条直线： 命令解析 → 读数据库 → 跑业务逻辑 → 写事件 → 飞书推送。 新架构的区别在于编排层两个兄弟并行工作： LangGraph 管流程推进（PM写完 → 触发 Planner 节点）， Blackboard 管跨 Agent 共享（PM 写入方案 → Blackboard 变了 → Redis Streams 唤醒 Planner Agent → Planner 从黑板读方案、写入任务清单提案）， 然后一起经过运行时和存储层。事件先写 Outbox 再异步投递，每步留审计痕迹、有幂等保护。

图 4.5 · 新老系统关系图（不是重复建设，是渐进替换）

一句话总结：两套系统同时在跑但互不干扰——老系统（单文件 CLI + SQLite）继续承载已验证的稳定业务， 新系统（agent_platform/）负责所有新功能。禁止双主写：任何一类数据任一时刻只有一个权威写入方。 最终目标是新系统完全接管、旧系统归档下线。下面这个时间线就是怎么一步步替过去的，不搞一次性推倒重写。

图 5 · 数据流程图（数据从哪来、存哪、给谁用）

一句话总结：唯一事实源是 PostgreSQL（老系统是 SQLite），所有东西都从它读写。 但数据也分"冷热"——任务/项目/审批这些结构化数据放主库， Agent 的思考过程、证据链、多专家辩论记录（Blackboard）是半结构化数据也在主库但加了版本管理， 语义检索走 pgvector 向量索引， 事件通知走 Redis Streams（只做唤醒、不当事实源）。 飞书、浏览器这些外部系统的东西，进来前先过工具网关校验权限、出去前过审计。
