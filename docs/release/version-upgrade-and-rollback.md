# 版本发布、升级与回退

## 目标与边界

`scripts/release_upgrade.py` 是 fail-closed 发布计划门禁，不直接操作集群、数据库或流量。它验证发布清单并输出有序升级计划和回退计划；部署控制器/操作人员负责执行每一步并留存执行证据。不得把“计划生成成功”当成部署成功。

## 发布清单

复制 `docs/release/UPGRADE_MANIFEST_TEMPLATE.json` 并为每次发布填写真实值。镜像必须使用不可变 digest；配置使用不可变 revision。清单要求：

- 起止 SemVer，且目标版本严格高于当前版本；
- 应用/Schema 兼容区间和旧、新版本可共存的兼容窗口；
- 迁移预检已通过、已验证备份引用，以及 expand/contract 策略；
- 滚动批次百分比合计 100%，每批必须经过健康门禁；
- 上一镜像、上一配置 revision 和不可变配置快照引用；
- Schema 回退只能选择无破坏性回退、补偿迁移或已演练的备份恢复。

## 迁移前检查

在任何写操作前执行并记录：目标环境/版本与镜像 digest、Schema 当前版本和漂移、迁移依赖顺序、锁与长事务风险、磁盘/连接池余量、复制延迟、后台任务积压、读写兼容性、备份完整性及隔离恢复演练。任一项未通过，禁止进入迁移和流量切换。

## 兼容窗口与滚动升级

先执行 expand migration（只新增兼容结构，不立即删除旧字段/索引），再进入兼容窗口。窗口内旧、新应用版本必须可同时读写；采用 5%/25%/70% 等分批方式（清单可配置且总和必须为 100%），每批观察健康、错误率、延迟、队列积压和依赖指标，健康门禁失败即停止后续批次并触发回退。兼容窗口关闭且确认无旧版本实例/旧格式消费者后，才允许单独执行 destructive contract migration。

## 回退策略

回退顺序：停止发布并摘除新版本流量 → 恢复上一不可变应用镜像 → 恢复上一配置快照 → 按清单执行补偿迁移或经过演练的备份恢复 → 验证旧版本健康。配置回滚必须恢复整套已知良好 revision，不做临时手工猜测式修改。

数据库 Schema 不保证可逆。若没有补偿迁移或已验证恢复演练，计划只保留向后兼容 Schema，要求 forward-fix；不得自动执行未经验证的 down migration。备份恢复会覆盖/丢失恢复点之后的数据，必须有明确审批、RPO/RTO 和数据核对方案。

## 使用

```bash
python scripts/release_upgrade.py --manifest path/to/upgrade-manifest.json
python scripts/release_upgrade.py --manifest path/to/upgrade-manifest.json --format text
```

门禁返回 0 表示清单结构完整、计划可生成；返回 1 表示清单不满足安全前置条件；返回 2 表示清单无法读取。脚本不会执行生产变更。
