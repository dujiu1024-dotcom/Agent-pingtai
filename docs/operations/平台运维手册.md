# 平台运维手册（C-18-05）

本文定义日常部署、升级、备份、恢复、回滚、验证与故障定位入口。生产操作仍须遵循变更审批、维护窗口和目标环境授权；脚本成功不等于生产灾备验收。

## 1. 前置条件

- Docker Engine 与 Docker Compose v2；Python 3；PostgreSQL 客户端工具、Redis CLI、MinIO Client、age、sha256sum。
- 从 `deploy/.env.example` 生成 `deploy/.env`，填写凭据和固定镜像版本/摘要。禁止提交真实密钥；`deploy/.env` 权限为 0600。
- 准备 age recipient（备份）与受控 identity（恢复），密钥通过环境变量/密钥管理系统注入，不写入命令参数或日志。
- 先确认目标环境、租户/数据范围、变更窗口、回退条件、负责人及通知对象。

## 2. 统一运维入口

所有命令从仓库根目录执行：

```bash
bash scripts/platform_ops.sh help
bash scripts/platform_ops.sh deploy
bash scripts/platform_ops.sh upgrade
bash scripts/platform_ops.sh verify
bash scripts/platform_ops.sh diagnose
bash scripts/platform_ops.sh backup
bash scripts/platform_ops.sh restore postgres
bash scripts/platform_ops.sh restore redis
bash scripts/platform_ops.sh restore object-storage
ROLLBACK_SNAPSHOT=deploy/releases/env-<成功快照> bash scripts/platform_ops.sh rollback
```

- `deploy` / `upgrade` 先执行 Compose 配置校验，再调用基础设施部署脚本；升级前须固定镜像 tag 或 digest，统一入口拒绝 `:latest`。
- `backup` 依次运行 PostgreSQL、Redis、MinIO 备份脚本。任一失败即停止；备份产物写入受限目录，需同时保留密文、SHA-256 和 manifest。
- `restore` 只分派到对应组件的受控恢复脚本。恢复前必须设置脚本要求的确认变量，并在隔离目标执行；禁止直接对生产目标试运行。
- `rollback` 仅回滚 Compose 环境配置/服务，不执行数据库 schema 逆向迁移，也不回滚业务数据。
- `verify` 校验 Compose 配置并检查服务运行/健康状态；不代表 API 端到端或真实数据恢复通过。
- `diagnose` 只输出 Compose 服务状态，不打印环境变量、密钥或容器日志。

## 3. 发布/升级流程

1. 核对发布版本、镜像摘要、迁移兼容窗口、备份最近成功时间和恢复可用性。
2. 执行 `bash scripts/platform_ops.sh verify`；失败则停止发布。
3. 在变更窗口执行 `bash scripts/platform_ops.sh backup`，核对每个组件的三件套及远端副本。
4. 运行迁移预检并执行受控迁移：`scripts/migrate_postgres.sh`。迁移使用 advisory lock/checksum；不自动生成逆向 SQL。
5. 执行 `bash scripts/platform_ops.sh upgrade`，随后执行 `verify`。检查 API/Worker 冒烟测试、关键队列和 Outbox 积压。
6. 若健康门禁失败，按变更预案选择配置回滚或应用版本回退；不要把基础设施配置回滚误当作 schema/data 回滚。
7. 记录版本、commit、镜像摘要、迁移版本、操作者、开始/结束时间、检查结果和回退决定。

## 4. 备份与恢复

组件级备份/恢复细节见：
- PostgreSQL：`scripts/backup_postgres.sh`、`scripts/restore_postgres.sh`。
- Redis：`scripts/backup_redis.sh`、`scripts/restore_redis.sh`。
- MinIO：`scripts/backup_object_storage.sh`、`scripts/restore_object_storage.sh`。

恢复必须先确认备份来源、manifest、校验和、加密身份及目标数据库/bucket；在隔离环境验证 schema、关键记录、租户边界、对象可读性和 Outbox 重放。Redis 丢失后的事件恢复应使用已授权的 PostgreSQL Outbox 重放流程，并保留 event_id 供消费者幂等处理。不要仅凭备份命令退出码认定恢复可用。

## 5. 故障排查

| 现象 | 检查 | 处理 |
|---|---|---|
| Compose 配置失败 | `docker compose config --quiet` | 检查必填变量、YAML 与镜像版本 |
| 服务未健康 | `platform_ops.sh diagnose`、Docker health 状态 | 检查依赖可用性、资源和探针；不要在报告中粘贴密钥 |
| 备份失败 | 工具依赖、磁盘空间、age recipient、目标权限 | 保留失败摘要；修复后重新生成完整备份三件套 |
| 校验和/manifest 不匹配 | 文件名、传输完整性、manifest | 隔离该备份，禁止恢复，重新从可信副本获取 |
| 恢复拒绝执行 | 确认变量、Redis 停服状态、目标路径权限 | 核对恢复准入条件；不得绕过显式确认 |
| 升级后异常 | 版本兼容、迁移 ledger、服务健康 | 按发布预案回退应用/配置；schema 回滚须有专门逆向迁移方案 |

## 6. 演练与运行记录

每次演练记录：演练编号、环境、数据分类、备份时间、组件、目标、操作者/审批人、开始/结束时间、脚本版本、校验结果、恢复后抽样验证、事件重放结果、实际 RPO/RTO、遗留问题和证据链接。

RPO/RTO 必须来自实际演练测量，不在手册中预填推测值。当前生产环境真实部署、恢复、故障切换与 RPO/RTO 测量仍需在授权目标环境执行。
