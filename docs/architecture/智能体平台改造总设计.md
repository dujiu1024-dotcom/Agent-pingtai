# 智能体平台改造总设计

- 版本：v1.1
- 日期：2026-11-15
- 状态：架构决策已冻结；平台能力基线与分阶段实施计划已补充
- 目标仓库：`dujiu1024-dotcom/Agent-pingtai`

## 1. 改造目标

将现有 FDE 单体式 Agent 工作台演进为可扩展、可审计、可部署的通用智能体平台。保留现有业务资产和已验证能力，通过模块化边界逐步替换运行底座，不进行一次性推倒重写。

平台核心能力：
1. 多专家 Agent 协作：共享黑板、任务分派、并行分析、质疑与裁决。
2. 工作流编排：用 LangGraph 承担有状态、有分支、可暂停恢复的流程。
3. Agent Runtime：通过 Harness 适配层接入可替换的 Agent 执行引擎。
4. 工具接入：兼容 MCP；能力说明优先采用 Agent Skills 开放格式。
5. 模型治理：统一模型网关与模板配置，不把模型名称散落在角色提示词或业务代码。
6. 监督式自主：低风险动作可自动执行；高影响动作必须进入审批与审计。
7. 企业级状态：PostgreSQL + pgvector 为持久化主库；Redis Streams 用于事件分发与唤醒。
8. 可观测：运行轨迹、Token/成本、工具调用、失败、审批和评测结果可追踪。

## 2. 已冻结的技术决策

| 决策 | 选型 | 边界 |
|---|---|---|
| 多专家协作 | Hybrid Blackboard | 共享事实/产物持久化；事件负责唤醒；工作流负责局部有序协作 |
| Agent 自主程度 | Supervised | 默认监督；审批前不得执行高风险副作用 |
| 模型配置 | Template | 按场景/角色引用模板；环境变量只覆盖密钥与部署参数 |
| 工作流 | LangGraph | 只用于显式流程、状态持久化、分支、人工介入；不取代黑板 |
| Harness | 适配层 | 优先接入成熟开源运行引擎；平台不自研模型执行循环 |
| 工具协议 | MCP | 工具发现、调用、权限和审计统一经过工具网关 |
| 能力封装 | Agent Skills | 角色/技能说明可移植；技能不持有平台权限 |
| 主数据 | PostgreSQL | 业务状态、黑板、运行、审批的事实源 |
| 向量检索 | pgvector | 与业务实体同库，按需建立索引 |
| 事件分发 | Redis Streams | 异步唤醒、消费组、重试；不作为业务事实源 |
| 可观测 | Langfuse（自托管） | 记录 trace、generation、工具调用和成本；不得记录明文密钥 |

## 3. 目标架构与职责边界

```
Web / API / CLI
      |
身份认证、租户隔离、RBAC、审计入口
      |
平台控制面
  |-- Agent / Skill / Tool 注册
  |-- 模型模板与策略管理
  |-- 项目、任务、运行与审批
  |
Orchestrator（LangGraph）
      |
Agent Runtime（Harness Adapter）
      |
专家 Agent 执行
  |-- 读取黑板上下文
  |-- 调用授权 MCP 工具
  |-- 产出结构化观点、证据和产物
  |-- 提交黑板变更提案
      |
Hybrid Blackboard
  |-- PostgreSQL：事实、观点、证据、关系、版本、裁决
  |-- Redis Streams：事件、唤醒、重试
  |-- pgvector：语义检索
      |
Langfuse / 审计日志 / 评测
```

控制面负责身份、配置、权限、审批和生命周期；编排层负责流程状态；Runtime 负责单次 Agent 执行；黑板负责跨 Agent 共享认知；工具网关负责外部副作用；存储层负责持久化。禁止让 Agent 直接访问数据库、Redis 或任意网络。

## 4. Hybrid Blackboard 数据语义

黑板不是聊天记录，也不是简单共享文本。每条写入必须有类型、范围、来源和版本。

### 4.1 作用域
- `run`：单次执行内部临时信息。
- `task`：当前任务的共享信息。
- `project`：项目长期事实与决策。
- `tenant`：租户级知识与策略。

### 4.2 核心对象
- `BlackboardEntry`：统一条目，包含类型、作用域、内容、作者、版本、状态。
- `Evidence`：来源、定位、摘要、哈希、可信等级。
- `Claim`：专家提出的可验证主张，必须关联证据或明确标注假设。
- `Challenge`：对主张的质疑、反证或缺口。
- `Conflict`：相互冲突的主张及其证据。
- `Decision`：裁决结果、裁决人/Agent、理由、引用条目和生效范围。
- `BlackboardEvent`：条目新增、变更、质疑、冲突、裁决等事件。

### 4.3 写入与并发规则
1. Agent 只能提交提案，不得覆盖其他 Agent 的条目。
2. 更新必须携带期望版本号，采用乐观并发控制。
3. 证据与原始来源不可被静默改写；更正以新版本追加。
4. 冲突先显式登记，不通过最后写入覆盖。
5. 裁决记录不可变；撤销或修正必须产生新裁决。
6. 事件采用至少一次投递，消费者必须幂等。
7. 黑板内容均保留创建者、时间、来源和审计关联 ID。

### 4.4 事件投递与消费恢复
- PostgreSQL Outbox 是待投递事件的事实源；Redis Streams 仅承载唤醒消息。
- Relay 通过租约和 `FOR UPDATE SKIP LOCKED` 并发领取；发布成功后使用租约令牌确认，过期租约可重新领取。
- 消费端使用 PostgreSQL `platform_event_receipts`，以租户、消费者和事件 ID 唯一约束处理回执。
- 回执状态包括 processing/completed/dead_lettered；processing 租约过期或失败释放后允许重试，completed/dead_lettered 事件不会再次调用业务处理器。
- Outbox 发布与消费失败均使用 PostgreSQL `next_attempt_at` 持久化指数退避，延迟封顶 300 秒；消费者在退避窗口内不会重复领取执行。
- Redis 传输层提供 Pending 数量、最早/最晚 Pending ID、消费者数量和 DLQ 数量查询，供健康检查与监控面板采集。
- 达到单事件最大执行次数（默认 5 次）后进入死信流程；无法解析的消息直接进入死信队列。
- Redis Pending Entries 通过 `XAUTOCLAIM` 由替代消费者恢复；消费成功后先完成数据库回执，再 ACK Redis。
- 死信处理先通过 Redis 事务将原始字段、失败原因、来源 Stream/消息 ID 写入独立 DLQ Stream 并 ACK 原消息，再更新 PostgreSQL 回执状态。Redis 写入失败时原消息保持 Pending；若数据库状态更新失败，DLQ 可能重复，需以来源消息 ID 去重。
- 该机制提供至少一次处理与数据库回执去重，不宣称外部副作用 exactly-once。处理器对邮件、支付等外部系统仍必须传递 event_id 作为幂等键，并经过平台工具审批。

## 5. Supervised 自主与审批策略

默认拒绝未声明权限的工具调用。动作按风险分级：
- L0 只读：读取已授权资料、检索、内部分析，可自动执行。
- L1 内部可逆写入：创建草稿、更新任务草案、写入黑板提案，可自动执行并留痕。
- L2 外部或不可逆动作：发消息、发布内容、提交外部系统、修改业务数据，必须人工审批。
- L3 资金/安全/权限动作：付款、签约、密钥管理、授权变更，必须由具备权限的人直接执行；Agent 仅可准备材料。

动作风险级别必须来自服务端可信工具注册表，严禁由模型输出或 Agent 参数自行声明。审批必须绑定动作参数摘要、目标资源、调用者、过期时间和一次性审批 ID。参数发生变化时原审批失效。审批通过不等于绕过工具权限检查。

## 6. 模型模板策略

模型配置以模板为唯一业务入口。模板至少包含：
- 模板 ID、版本、用途、默认模型、备用模型。
- temperature、top_p、max_tokens、timeout、重试策略。
- reasoning 配置、结构化输出约束。
- 成本/速率限制、数据分级、允许工具范围。
- 适用 Agent/工作流与灰度状态。

Agent 仅引用 `model_template_id`，不硬编码模型名。模型供应商通过 OpenAI-compatible 等统一适配接口接入。密钥只从 Secret/环境变量注入，不进入模板文件和数据库明文。

## 7. 开源组件接入原则

| 组件 | 用途 | 采用方式 |
|---|---|---|
| LangGraph | 状态化工作流 | 直接复用，业务流程节点由平台注册 |
| Harness 实现 | Agent 执行循环、上下文与工具执行 | 先做适配器 PoC，优先复用成熟项目，不复制其核心循环 |
| MCP Python SDK | MCP 客户端/服务端协议 | 直接复用 |
| Agent Skills | 技能描述与可移植能力包 | 采用开放目录约定和元数据 |
| PostgreSQL | 事务型持久化 | 主数据源 |
| pgvector | 向量字段与近似检索 | PostgreSQL 扩展 |
| Redis Streams | 事件分发与消费组 | 仅做消息层 |
| Langfuse | Trace 与成本观测 | 自托管，可关闭/替换 |

Harness 具体实现必须经过独立 PoC：验证工具调用循环、权限拦截、流式输出、取消/超时、上下文压缩、结构化输出、运行恢复和许可证。PoC 未通过前不得将某个项目写死为平台唯一运行时。

当前已建立 DeepSeek Harness 与 Strands Agents 两个适配器入口。Strands 适配器使用 OpenAI-compatible 受控代理、禁用工具目录和插件；工具只能经由受信任的 run-scoped Gateway MCP Provider 注入，并提取 token/延迟指标；DeepSeek Harness 仍要求独立容器隔离。两者尚未接入真实模型进行同任务成本/质量对比，不能据此宣布选型完成。已提供同任务基准测试运行器：固定任务输入、逐个运行适配器、记录确定性验收点、延迟、Token 用量和异常；该验收点只用于基础回归，不替代人工质量评审或模型裁判。
多专家工作流增加 LangGraph 真实运行时集成测试，覆盖专家并行汇聚、证据冲突解决、人工审批中断与恢复、拒绝分支及免审批归档。


### 7.1 Gateway-only MCP Profile（首版安全边界）
- 每个 Agent Run 创建独立 `GatewaySessionContext` 与 MCP Server 实例；禁止跨租户、跨 Run 共享实例。
- `tenant_id`、`actor_id`、角色、Run/Agent 标识、允许工具集合和审批 ID 均由可信控制面注入，不从模型工具参数或 MCP 请求体读取。
- 工具发现只暴露当前 Run 白名单内且角色匹配的工具；未登记、未授权或未配置 JSON Schema/资源解析器的工具不允许暴露。
- 每个工具必须声明 JSON Schema（对象类型且 `additionalProperties=false`）、服务端资源解析器、资源授权器和租户感知的处理器；参数在进入 Gateway 前校验，资源标识由服务端从已校验参数解析，资源授权器在执行前校验当前租户/角色是否可访问该资源。
- L2 审批 ID 按动作 SHA-256 摘要从可信会话上下文中查找并注入，不能由模型自行传入；摘要绑定动作、资源、调用者和参数，参数变化会导致审批失败。
- 所有调用最终进入 `SupervisedToolGateway`，沿用角色、风险、一次性审批、写前审计和结果审计逻辑；审计记录同时保存 tenant、run、agent、actor、工具、资源、参数摘要和执行结果；MCP Server 不直接连接业务系统。
- MCP Server 只负责协议适配，必须由宿主绑定到受控传输与身份认证。当前工厂返回 per-run Server 实例，不提供匿名网络监听，也不宣称已经完成 Harness 侧真实连接。
- 当前首版已具备 MCP SDK Server 工厂、会话级工具白名单和越权测试，并通过 MCP SDK 内存传输完成 ClientSession → tools/list → tools/call 的协议级集成测试。Strands 适配器已实现 Gateway Tool Provider 接口及官方 MCPClient Provider：通过可信 endpoint resolver 获取当前 Run 的 HTTPS endpoint 和短期 Bearer Token，MCPClient 仅发现白名单内工具，且 Provider 会校验发现结果与白名单完全一致；连接在 Agent 执行期间保持，结束或异常时关闭。MCP 服务端必须在认证时将短期 Token 映射到不可变的 Run/租户/角色/审批上下文。当前已完成 Provider 生命周期与失败关闭测试；Gateway endpoint 的生产服务化、Token 签发/撤销、真实网络端到端调用、取消传播和断连演练仍是后续验收项。

## 8. 与现有仓库的兼容策略

现有 `agency.py`、`db.py`、`boss.py`、`conversation.py`、`vectors.py`、飞书接入和既有 Agent 角色是存量资产：
- 第一阶段只建立新平台边界与适配层，不删除、不大规模重构存量代码。
- 通过 Adapter 逐步接入现有模型调用、角色定义、黑板事件和记忆检索。
- 新功能优先落在 `agent_platform/`，不继续扩大单体文件。
- PostgreSQL 上线前，SQLite 保持现有业务运行；迁移必须有双读校验/导出备份/回滚方案。
- Redis 不保存唯一业务状态；Redis 故障时事件可从 PostgreSQL outbox 重放。
- 新旧系统并行期间，明确每类数据的唯一写入方，禁止双主写。

## 10. 第一阶段验收标准

1. 新平台包可独立导入，不影响现有 CLI。
2. 无数据库、Redis、模型密钥时，基础单元测试可运行。
3. Blackboard 支持多作用域、提案、版本冲突和追加式裁决。
4. 同一事件重复消费不会重复执行副作用。
5. L2/L3 动作没有有效审批时必定被拒绝。
6. 模型模板不含任何真实密钥，Agent 不直接指定模型供应商密钥。
7. LangGraph/Harness/MCP 依赖隔离，组件缺失时给出明确错误而非导入阶段崩溃。
8. 现有测试与 CLI 行为不被本阶段改动破坏。

## 11. 明确不做

- 不自研 LLM 推理/工具调用循环。
- 不采用 Agent 间自由聊天作为协作主机制。
- 不让 Redis 成为业务事实源。
- 不允许 Agent 绕过审批直接执行高风险外部动作。
- 不在本阶段删除现有 FDE 工作台、飞书集成或 SQLite 数据。
- 不一次性重写 `agency.py`。

### 12.1 模型与知识边界补充
- Blackboard 是任务执行期多 Agent 共享认知与裁决记录，不替代知识库或长期记忆。
- Knowledge Base 管理外部资料的文档版本、切片、索引、ACL 和来源引用；pgvector 仅为向量存储能力。
- Memory 管理跨会话可复用的用户/Agent/项目状态；不得将完整对话无差别永久写入。
- Conversation 保存交互历史；Run/Task 保存执行生命周期；Trace 保存诊断链路，四者不得混为一个对象。

### 12.2 领域模型与物理模型说明
