# 落差清单：代码实现 vs 设计意图

> 判定方法：只认能在代码里找到**写入点/调用点**的东西。表 0 行且全仓库无引用的，直接判“空壳”。
> 数据快照：2026-11-12，`agency/state/agency.db`，schema v5，21 张表。

## 一句话结论

**不是“没有落差”，而是落差集中在“看起来有、实际没接上”**：19 种事件类型只用了 8 种；21 张表里 5 张从未被代码读写；11 个角色之间零调用；所谓提醒、文档同步、知识图谱、飞书任务映射，全部只有表结构，没有运行逻辑。

## 二、事件：19 种类型，只有 8 种真的会被发出

代码里所有 `log_event(...)` 调用点只有这些：

| 真的会发出 | 证据 |
|---|---|
| `task_created` | `agency.py:696, 989`；`console.py:476` |
| `tasks_created` | `agency.py:991` |
| `task_closed` | `agency.py:724`；`console.py:490` |
| `gate_confirmed` / `gate_revoked` | `agency.py:343/358/2857/2869` |
| `agent_run` | `agency.py:1117/1899` |
| `audit_flag` | `agency.py:1905` |
| `check` | `agency.py:1514` |

**永远不会发出**（`db.py:30–37` 有定义，但全仓库无 `log_event` 调用）：
`project_created`、`project_confirmed`、`task_due_soon`、`task_overdue`、`task_blocked`、`milestone_hit`、`milestone_deviation`、`gate_blocked`、`sync_conflict`、`doc_ready_review`、`contract_signed`、`invoice_overdue`。

**直接后果**：`subscriptions` 表里 5 条启用订阅，其中 3 条永远等不到事件——

- `task_due_soon → secretary:notify`
- `task_overdue → secretary:notify`
- `invoice_overdue → finance:notify`

也就是说，“临期/逾期自动提醒”“发票逾期提醒”在代码层面**不存在**，只有订阅记录摆在那里。真正跑通过的是 `task_created → secretary:notify`（9 条投递标记）和 `audit_flag → auditor:run`（4 条投递标记 + 1 条死信）。

## 三、实现和设计意图不一致

### 3.1 任务状态机是“二态”，不是六态

- `db.py:26` 定义 6 个状态：`todo/doing/blocked/review/done/closed`。
- 代码只写两个：建任务固定 `'todo'`（`agency.py:687`、`console.py:467`），关任务固定 `'closed'`（`agency.py:720`）。
- `_task_view()`（`agency.py:160`）把非 `closed` 全部折叠成 `"open"`，前端拿不到“在做/阻塞/待评审”。
- 当前库：23 条 `closed`，7 条 `todo`，其余 4 个状态 0 条。

**影响**：看板上的“进行中/临期/逾期”是 `task_state()` 按日期算的展示值，不是真实工作状态；无法回答“这条到底卡在哪”。

### 3.2 事件去重实际等于“不去重”

`log_event()` 的 `dedup_key = hash(微秒时间 | 类型 | ref | detail)`（`agency.py:392–404`）。时间精确到微秒，所以同一个人重复执行同一动作，几乎必然生成不同 key。

真正的幂等不在 `events` 表，而在投递侧的 `config_kv` 标记 `sync.delivered.<event_id>.<target>.<action>`（`agency.py:1241`）。注释写的“重复调用不会产生重复事件”与实现不符。

### 3.3 审计不是“独立 Agent”

- 角色卡里审计“独立监督、直属创始人”，但运行时和别的角色**同一个执行器、同一个进程**，只是 `ROLE.md` 不同。
- 真正的自动审计是 `audit_output()`（`agency.py:1991`）：用正则查产出里有没有输入中不存在的日期。它不查数字来源、不查报价、不查合同，也不冻结文档。
- `run` 失败只写 `agent_runs.ok=0`，**不进 `dead_letter`**；只有 `dispatch` / `sync` 失败才进死信（`agency.py:1163`、`1397`）。失败账本有两套。

### 3.4 日 token 闸可以被自动路径绕过

`token_gate()` 只在 `cmd_run()`（1875 行）和 `plan_from_llm()`（1013 行）调用。`_dispatch_execute()` 和 `sync_pending()` 的 `run` 分支**不检查日上限**，只受单次 dispatch 预算（默认 20000）和订阅预算约束。也就是说：手工跑会被日闸拦，自动派活不会。

### 3.5 控制台能写“非法 kind”

`console.py:448`：`kind = str(data.get("kind") or "plan")`。而 `db.TASK_KIND = ("general", "code")`，且 `tasks.kind` 没有 CHECK 约束。控制台新建任务时如果不传 `kind`，会写入 `kind='plan'`，随后 `check_consistency.validate()` 会把它判为“kind 非法”。

**当前库里还没出现**（30 条都是 general/code），但这条分支是真实可达的。

### 3.6 两套意图识别，行为不一致

- 控制台：`console.py` `diagnose_intent()`，纯关键词打分，不调模型，不花钱。
- 飞书：`listener.py` `intent_classify()`，调一次 LLM（`max_tokens=200`），失败才降级到关键词。
- 飞书这次 LLM 调用**不走 `ratelimit.py`，也不写 `agent_runs`**，所以既不受限流保护，也不进 token 账。

同一个“帮我看看项目咋样”，在控制台和飞书可能得到不同角色建议。

### 3.7 事实不进向量检索

- `facts` 表的事实只在 `build_prompt` 里按“最近 8 条”注入（`recent_facts()`，1584 行）。
- `vectors.index_path/index_all` 只收 `.md/.txt` 文件，**没有任何代码把 `facts` 写进 `embeddings`**。
- 结果：问“上次客户说的定价是多少”，语义检索找不到，只能碰运气看最近 8 条里有没有。

### 3.8 六槽位记忆实际只用了一个槽

当前 `wm_session` 13 行里：
- `constraints` / `decisions` / `open_questions` 多数是 `[]`（2 字节）；
- `digest` 只有 T-0011/pm 有 115 字节，其余为空；
- 真正有内容的是 `artifacts`（最近产物列表）。

`memory.py` 里“超预算先压 digest、再减产物、最后截约束”的压缩逻辑（177–195 行）**没有被真实压力场景触发过**。

### 3.9 导出包会带上全部 Agent 产出

`cmd_export()`（`agency.py:2901`）的 `include` 列表里包含 `agency/outputs`，而 `README.md` 写的是“自动排除 .env、outputs、WAL”。代码与说明相反。产出里可能含客户信息，导出给别人时会一起带走。

### 3.10 一致性检查是“项目专用 + 可跳过飞书”

- `tools/check_consistency.py` 硬编码 `BASE_TOKEN`、`TABLE_ITEM`、`CLIENT = clients/002-FDE一人公司`，只比对 `T-0008~T-0015` 这 8 条主任务的工时（`P0_TO_TASK`）。
- 飞书比对失败时只打印 `[提示] 飞书跳过：...`，**不置失败**（352–359 行）。所以“一致性全绿”可能是在没连上飞书的情况下得到的。
- 它也不是通用校验器：换客户、换项目就要改代码里的常量。

### 3.11 商务闸门对当前项目是“永久关闭”状态

`finance_gate_report()`（259 行）要求至少一张报价单 + 一份合同 + 开票信息。当前 `quotes`/`contracts` 都是 0 行，所以：

- 现在给 OPC-002 新建任何 `kind=code` 任务，都会被 `cmd_task_add` 的商务闸门拒绝；
- `gate finance confirm` 也会 `sys.exit(1)`。
- 历史上那 3 条 code 任务（T-0008/9/10）能存在，是因为 `cmd_migrate_json()` 直接 `INSERT INTO tasks`，**绕过了闸门**（`agency.py:486–506`）。

这说明闸门只在“命令行新建”这一条路上生效；迁移、直接写库、控制台（只查开工闸门，不查商务闸门，`console.py:456`）都能绕过去。

### 3.12 没有定时器，“事件驱动”靠人踢

- 全仓库没有 `cron`、`launchd`、`schedule` 相关代码。
- `sync` 必须由命令行、控制台按钮或飞书 `/sync` 触发；且只在本地 09:00–23:00 生效（`sync_window_ok`）。
- `check` 同样靠人跑，跑完只打印 + 写一条 `check` 事件，不投递提醒。
- `run-listener.sh` 只守护飞书长连接进程，不守护 `sync`/`check`。

### 3.13 3D 办公室是“展示层演出”，不是真实状态

- 页面数据全部来自 `console.py snapshot()` 的数据库快照；
- 人物走动、工位、闲聊是 `console.html` 前端动画；
- 服务端只提供 `RUNNING`（当前控制台内存里正在跑的角色）和 `agent_runs` 最近记录。
- 所以“看到某人在忙”不等于“某角色真在跑”，刷新页面也不会恢复真实运行态。

### 3.14 飞书任务读取本身不可靠

`feishu_bot.task_list()` 的注释自己承认：“飞书任务列表接口通常要求 user_access_token。应用身份调用可能返回权限错误”（282–291 行）。也就是说，即使以后接上 `feishu_tasks` 表，用应用身份也读不全任务列表。

## 五、如果只改三处，先改哪三处

1. **补事件产生点**：在 `cmd_check()` 里按 `task_state()` 生成 `task_due_soon` / `task_overdue`，在发票查询里生成 `invoice_overdue`。否则秘书/财务的提醒订阅永远是摆设。
2. **统一状态机**：建任务后允许写 `doing`，派活成功写 `doing`，产出待审写 `review`，并让 `_task_view` 不再折叠状态。否则看板永远只有“开/关”。
3. **堵住闸门旁路**：`console.create_task` 增加商务闸门检查并修正 `kind` 默认值；`migrate-json` 导入 `kind=code` 时至少打警告。否则“闸门”只是命令行装饰。

## 六、明确说“没有”的部分

- **没有**任何 Agent 之间的直接调用（无 A→B 派活代码）。
- **没有**定时任务/调度器（无 cron、无 launchd、无内置 scheduler）。
- **没有**自动把产出推送到飞书文档的实现（`docs` 表零引用）。
- **没有**自动通知客户、自动开票、自动对账的代码路径。
- **没有**知识图谱的读写实现（只有两张空表）。
