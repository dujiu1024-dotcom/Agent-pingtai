只根据代码推导，不引用设计文档。写给不懂技术的创始人看。

代码基线：2026-11-12 数据库：agency.db · schema v5 · 21 张表 主程序 3374 行 · 纯标准库

先记住三句话

1 个执行器，11 份提示词角色不是常驻员工，是每次被叫醒时读一遍 ROLE.md 的模型调用。
唯一事实源是一个 SQLite 文件命令行、控制台、飞书都只是入口，最后都回到 agency.py 和 agency.db。
“自动”比看起来少事件要人踢 sync，提醒没有定时器，产出不会自动进飞书，角色之间零调用。

落差清单：看起来有、实际没接上

判定标准：表 0 行且全仓库无引用 = 空壳；事件类型有定义但无 log_event 调用 = 永不触发。

一、空壳表（0 行 + 业务代码零引用）

表现状直接后果
reminders空壳 仅 db.py 建表“到点提醒”没有实现，只有手动 check
feishu_tasks空壳 仅 db.py 建表飞书任务映射层不存在
docs空壳 仅 db.py 建表文档登记、密级 L1–L4、飞书同步全空
entities / relations空壳 零读写知识图谱是纯占位
quotes/contracts/invoices/payments/costs全 0 行财务只有录入工具，没有业务数据

二、永远不会触发的事件（19 种定义，只发出 8 种）

真正会发出的只有：task_created、tasks_created、task_closed、gate_confirmed、gate_revoked、agent_run、audit_flag、check。

因此这 3 条已启用的订阅永远等不到事件：task_due_soon → secretary:notify、task_overdue → secretary:notify、invoice_overdue → finance:notify。临期/逾期提醒、发票逾期提醒在代码层面不存在。

三、实现与意图不一致（挑最关键的）

落差代码事实影响
任务状态机是二态只写 todo / closed；_task_view 折叠 open/closed看板看不到“在做/阻塞/待评审”
事件去重形同虚设dedup_key 含微秒时间戳同一动作重跑会重复产生事件
审计不独立与其它角色同一执行器；自动审计只是日期正则不查数字来源、不查报价/合同、不冻结文档
失败账本两套run 失败写 agent_runs.ok=0；dispatch/sync 失败才写 dead_letter手工失败不进死信，容易漏看
日 token 闸可绕过token_gate 只在 run / plan 调用dispatch 与事件唤醒不检查日上限
控制台可写非法 kindconsole.py:448 默认 kind="plan"，db 只认 general/code能写进校验器判非法的数据
两套意图识别控制台规则打分；飞书调 LLM 200 tokens行为不一致，飞书这次调用不限流、不记账
事实不进向量检索facts 只按最近 8 条注入；index 只收文件语义检索搜不到历史事实
六槽位只用了一个多数槽位是 []；digest 仅 1 条有值记忆压缩逻辑没被真实压力验证
导出包含客户产出cmd_export 的 include 含 outputs与 README“排除 outputs”相反
一致性检查可跳过飞书飞书比对失败只打印提示，不置失败“全绿”可能是没连上飞书
商务闸门被旁路quotes/contracts 0 行 → 新 code 任务必被拒；历史任务由 migrate-json 直接 INSERT闸门只管命令行一条路
没有定时器无 cron / launchd；sync 和 check 靠人触发“事件驱动”实际是“人驱动”
3D 办公室是演出页面读数据库快照；人物动画在前端看到“有人在忙”不等于真在跑

四、如果只改三处

  • 补事件产生点：在 check 里生成 task_due_soon / task_overdue，在发票查询里生成 invoice_overdue，否则提醒订阅永远是摆设。
  • 统一状态机：派活写 doing，产出待审写 review，前端不再折叠状态。
  • 堵住闸门旁路：控制台补商务闸门并修正 kind 默认值；migrate-json 导入 code 任务时至少告警。
