### N04｜`dep='—'` 被当成真实依赖，4 条 open 任务永远派不出去（P0）

  - 真实数据：`T-0028/T-0029/T-0030/T-0031` 的 `dep` 都是 `'—'`，`_dep_list` 返回 `['—']`，而 `'—'` 永远不在 closed 集合里。
  - 实测 `dispatch_ready` 返回 `['T-0011','T-0032',...]`，**不包含这 4 条**；但它们的状态是“临期/进行中”、owner 是 secretary/content/scout/pm、今天都在窗口内。
- **真实影响**：本周三条真实业务任务（T-0028/29/30）和 T-0031 永远不会被自动派活。UI 上显示“临期”，但没有“为什么不能派”的提示。这是“看着对、跑起来不对”的典型。
- **第一轮未覆盖原因**：第一轮只审代码分支，没有检查真实 `dep` 字段的取值；把“依赖全关”当成正常逻辑，没有代入占位符数据。
- **修复成本**：0.5h（`_dep_list` 过滤 `—/-/无/none`），优先级 P0。

### N05｜完全相同的任务可以重复创建，没有内容级幂等

## 3. 并发与异常输入（新增 4 项 + 附录）

### N10｜导入会静默覆盖非空目录里的代码和数据库（P0）

- **证据**：`cmd_import` 只 `target.mkdir(parents=True, exist_ok=True)`，不检查目录是否为空、不备份、不询问（`agency.py:3055-3060`），随后 `extractall` 直接覆盖。
- 实测：在已恢复的目录里给 `agency.py` 加一行 MARKER，再执行一次 import，MARKER 消失；`agency/state/agency.db` 被包内旧库覆盖。
- **真实影响**：把备份恢复到正在使用的目录，会**静默回滚数据库和代码**，丢掉导入后新增的任务/事件；没有任何提示或 `.bak`。
- **第一轮未覆盖原因**：第一轮只审“导入包是否缺文件”，没有审“导入目标已存在时会发生什么”。
- **修复成本**：2h（非空拒绝或 `--force` + 自动备份 + 先解到临时目录），P0。

### N11｜导入不是原子的，失败会留下半成品目录

- **证据**：`tar.extractall(target)` 直接写目标目录，没有 staging/rename（`agency.py:3060`）。
- 实测：构造“先写 ok.txt，再放一个绝对符号链接”的包，在 Python 3.14 上导入中途抛 `AbsoluteLinkError`，退出码 1，但 `/tmp/fde-partial/ok.txt` 已经落盘。
- **真实影响**：失败后用户会看到一个“部分恢复”的目录，`doctor` 可能一半绿一半红；重试又叠加文件。没有任何“全有或全无”。
- **第一轮未覆盖原因**：第一轮只审路径穿越校验，没有构造“中途失败”的包。
- **修复成本**：2h（解到临时目录，成功后原子替换），P1。

### N12｜飞书事件去重只存在内存里，进程重启后重放会再次执行

- **证据**：`listener._SEEN` 是 `OrderedDict` + `threading.Lock`，`_SEEN_MAX=500`、`_SEEN_TTL=300s`，只在进程内（`listener.py:43-63`）；`on_message` 用 `message_id` 做首次判断（`listener.py:300`）。没有落库、没有用 `events.dedup_key`。
- **真实影响**：listener 重启（守护脚本 5 秒拉起）后，飞书重投/人工重放同一条消息会再次执行 `/task add`、`/run`，产生重复任务或重复 token 花费；超过 5 分钟的重投也会再次执行。
- **第一轮未覆盖原因**：第一轮只审白名单绕过，没有审“去重状态的生命周期”。
- **修复成本**：2h（message_id 落 SQLite + 与 events 去重键统一），P1。

### N13｜负工时被接受，直接污染 WBS 与完成度

- **证据**：`--hours` 是 `type=float` 且无范围校验（`agency.py:3084`、`3101`）。实测 `task add --hours -5` 和 `update --hours -7` 都成功，库里出现 `-5.0`、`-7.0`。

## 5. 导出导入往返真实性（新增 2 项 + 附录）

### N15｜导入不校验包完整性，坏包也打印“已恢复”

- **证据**：`cmd_import` 只检查路径安全，然后 `extractall`，最后打印“已恢复到 … / 下一步 doctor”（`agency.py:3053-3063`）；不检查必需文件、不自动跑 doctor、不校验 DB 版本。
- 实测：缺 8 个模块的包导入退出码 0，用户下一步才在 doctor 看到 ImportError。
- **真实影响**：自动化脚本会认为恢复成功；备份是否可用要等人工发现。与“解压即用/整包迁移”的承诺冲突。
- **第一轮未覆盖原因**：第一轮只证明“导出的包缺文件”，没有审“导入端是否应该拒绝坏包”。
- **修复成本**：2h（manifest + 必需文件/版本校验 + 可选 doctor），P1。

### N16｜WAL checkpoint 失败被吞掉，导出可能丢最近写入

- **证据**：`cmd_export` 把 `PRAGMA wal_checkpoint(TRUNCATE)` 包在 `try/except` 里，失败只打印提示并继续（`agency.py:3029-3033`）；而 `-wal/-shm` 又被排除在包外。
- **真实影响**：如果 checkpoint 失败（锁、磁盘、权限），最近已提交但还在 WAL 里的事务不会进包，恢复后“少了几条任务/事件”，且导出方看到的是“已导出”。
- **第一轮未覆盖原因**：第一轮只提到“导出排除 WAL”，没有审 checkpoint 失败后的行为。
- **修复成本**：1h（checkpoint 失败即中止，或改用 SQLite backup API），P1。

### N18｜事件流用本地时间，Agent 运行/任务详情用原始 UTC，同一页面两套时区

- **证据**：`console.html` 的 `evTime()` 用 `new Date(v).toLocaleTimeString('zh-CN')` 转本地（1908-1912）；而“最近产出”直接用 `String(r.created_at).slice(5,16)`（1869）、任务详情 `created_at/closed_at` 也直接 `slice`（1976-1977）、事实日期 `slice(0,10)`（2132）。
- **真实影响**：同一条任务，事件流显示 15:40，任务详情显示 07:40；跨零点的事实日期可能差一天。排查“什么时候关的/什么时候跑的”会看错 8 小时。
- **第一轮未覆盖原因**：第一轮只审后端 `daily_token_usage` 的 UTC/本地日期口径，没有审前端展示层。
- **修复成本**：1h（统一 `evTime`/`toLocaleString`），P2。

### N19｜`delivered_at` 截断到秒，已出现 2 条“投递早于创建”

- **证据**：事件 `created_at` 带微秒，`delivered_at` 用 `timespec="seconds"`（`agency.py:1430`）；实测 events 98、100 的 `delivered_at < created_at`（相差不到 1 秒）。
- **真实影响**：任何“投递耗时/延迟”统计会出现负数；按时间排序时可能把投递事件排在创建前。
- **第一轮未覆盖原因**：第一轮只审事件字段含义，没有做时间先后的一致性查询。
- **修复成本**：0.5h（统一精度或比较时截断 created_at），P2。

## 8. 本轮之后仍无法担保穷尽的部分

这轮能担保的是：**上面 20 条都真实存在，且大部分有运行证据**。仍不能担保穷尽，原因是以下几类没有足够手段：

1. **真实外部服务的行为**：飞书/Lark 接口版本、字段变更、限流；模型端点的非标准字段、上下文上限、错误文本差异；Ollama 模型缺失。本轮只用 fake sender/runner 或代码推断，没有真实账号/真实模型做契约测试。
2. **长时间运行与崩溃恢复**：SIGKILL 发生在 `sync` 发消息与写标记之间、导出/导入中途、SQLite checkpoint 中途；断电/WAL 损坏；磁盘满。本轮只做了“导入中途失败”一个场景。
3. **OS/GUI 操作层**：Peekaboo、OpenClaw、屏幕录制权限、锁屏/睡眠、窗口焦点。测试覆盖率高（browser 73.9%、gui 81.1%），但都是 mock/浅层，不等于真实桌面可用。
4. **规模与并发**：>1 万任务、>10 万向量、10+ 并发写、长时间事件积压。本轮只做了 8 路并发和单次锁竞争。
5. **安全对抗**：除 tar 穿越、CSRF/Host、路径穿越外的 SSRF、XSS、SQL 注入、依赖供应链、提示词注入的完整利用链。
6. **多用户/权限模型**：当前默认单用户；没有角色/租户隔离，跨项目读产出已发现，但更大范围的越权未测。
7. **历史数据迁移**：v1→v5 各版本的真实旧库、旧 JSON、缺失字段、重复 ID；本轮只用了 v5 库。
8. **模型输出质量**：事实准确性、引用完整性、幻觉率。覆盖率和断言都测不了语义正确性。
9. **前端 3D/交互**：console.html 的渲染、动画、响应式、浏览器兼容，没有 e2e。
10. **备份恢复演练**：没有在“断电/中断/半包/旧版本”组合下做过完整恢复演练。

### 要真正担保，需要引入的手段

- **覆盖率门禁**：CI 里跑 `coverage`，设总行覆盖 ≥70%、`agency/db/vectors/console` ≥80%、`listener/feishu_bot` 必须 >0；再加分支覆盖门槛。低于阈值直接失败，不允许“测试通过但没跑到”。
- **入口级冒烟**：CI 用子进程跑 `doctor`、`task add/close`、`check`、`sync --dry-run`、`export → 干净目录 import → doctor`，断言退出码和落库结果；不是只调函数。
- **契约测试**：用 fake Feishu/LLM 做日常 CI，另设 nightly 用真实端点跑 1 条最小链路；端点变更能提前暴露。
- **故障注入**：在 import/export/sync 中途 `kill -9`，断言“要么全成、要么全无”；SQLite 锁/磁盘满/只读目录。
- **压测基线**：1 万任务、10 万向量、10 并发写，记录 `dispatch`、`search`、`/api/state` 的 p95；超过基线告警。
- **安全用例集**：CSRF/Host、tar 符号链接、`/api/output` 跨项目、飞书重放、白名单外聊天。
- **迁移测试**：为 v1–v5 各留一个 fixture 库，CI 跑升级 + 数据核对。
- **依赖锁定**：`requirements-listener.txt` 锁版本 + 定期升级测试；Python 版本矩阵（3.9/3.12/3.14）。
- **E2E**：Playwright 跑控制台四个视图 + 派活 + 关任务 + 打开产出。
